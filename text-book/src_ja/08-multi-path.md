# マルチパス探索を「ゴミの山」にしない方法

![イラスト](images/08_exploration_branches.png)


## イントロダクション：「柔軟な探索」から「何も動かせない状態」へ

![研究の分かれ道](images/comics/08_crossroads.png)

研究プロジェクトが始まって3ヶ月。あなたは勤勉な研究者として、多くの異なる方向性を試してきました。

- パス A：モデルアーキテクチャの改善（5種類の異なるアテンション機構）
- パス B：訓練戦略の最適化（3種類の異なる学習率スケジューリング）
- パス C：データの質の向上（4種類の前処理方法）
- パス D：損失関数の調整（6種類の異なる損失の組み合わせ）

あなたは興奮していました。これほど多くの探索をしていれば、必ず有効な組み合わせが見つかるはずだ！

しかし、プロジェクトのディレクトリを開いてみると、そこには次のような光景が広がっていました。

```text
experiments/
  train_v1.py
  train_v2.py
  train_v2_fixed.py
  train_v3_final.py
  train_v3_really_final.py
  train_attention_test.py
  train_loss_ablation.py
  ...（計20以上のファイル）

outputs/
  run_0523/
  exp_new/
  test_attention/
  final_results/
  final_results_v2/
  backup_0601/
  temp/
  ...（計50以上のディレクトリ）

configs/
  config.yaml
  config_old.yaml
  config_backup.yaml
  config_test.yaml
  ...（計15以上のファイル）
```

**そして、問題が露呈し始めます。**

### 問題1：最良の結果が見つからない

ある時の実験結果が非常に良かったことは覚えています。しかし、それがどの設定で、どの出力ディレクトリにあるのかを思い出せません。ディレクトリを一つずつ開き、ログを確認しながらその結果を探すのに2時間を費やしましたが、結局正しく見つけられた確信が持てません。

### 問題2：何も削除できない

`outputs/` はすでに50GBの容量を占めています。しかし、どのディレクトリも怖くて削除できません。万が一、削除したのが論文に必要なあの実験だったら……？ 結局「とりあえず残しておこう、HDDの容量はまだあるし」と決断を先送りにします。

### 問題3：異なるパスを比較できない

![08 10 path comparison](images/comics/08_10_path_comparison.png)

「パス A（アテンションの改善）」と「パス B（学習率の最適化）」の効果を比較したいと考えましたが、次のことに気づきます。

- 使っているベースラインが違う（一方は3ヶ月前のもの、もう一方は最近のもの）。
- 評価スクリプトが違う（一方は Top-1、他方は Top-5 を算出している）。
- データの分割方法も違うかもしれない（記憶が定かではない）。

### 問題4：有効な改善をマージできない

パス A で有効な改善を見つけたので、それをパス B に移植しようとしましたが、以下の問題に直面します。

- パス A とパス B のコードがすでに乖離（デバージェンス）している。
- データロードのロジックに互換性がない。
- マージには膨大な手作業が必要になる。

**あなたは気づきました。「柔軟な探索」が無秩序な混乱に、「マルチパスの並行作業」がゴミの山に変わってしまったことに。**

## なぜマルチパス探索は制御不能に陥りやすいのか

研究の本質は **不確実性** です。どの道が成功するか分からないため、同時に複数の方向を探索する必要があります。しかし、管理メカニズムがなければ、探索の量が増えるほど混乱度も増していきます。

### 崩壊の3つのステージ

#### ステージ1：急速な探索（1〜4週目）

**行動**：
- 思いついたことは何でも試す。規範にとらわれない。
- コードはコピペ。名前を変えてすぐ使う。
- 出力は適当な場所に置く。「とりあえず動かすのが先決」

**感覚**：活気に満ち、進展が速い。

#### ステージ2：パスの乖離（5〜8週目）

**行動**：
- 異なるパスのコードが乖離し始め、共通部分が減る。
- 各パスが独自のデータ処理、訓練スクリプト、評価方法を持つようになる。
- 新しいアイデアがメインラインではなく、古い特定のパスに基づいたものになる。

**感覚**：少し散らかってきたが、まだ大まかには把握できている。

#### ステージ3：制御不能な混乱（9週目以降）

**行動**：
- どの実験がどのパスのものか全く思い出せない。
- 怖くて何も消せず、ディスク容量が爆発する。
- 改善をマージしようとしても、パス間の互換性が完全に失われている。
- 論文のために実験を再実行すると、記憶と結果が合わない。

**感覚**：焦り、無力感。すべてを白紙にしてやり直したいという衝動。

### 根本原因：「破棄可能性」と「マージ可能性」の欠如

マルチパス探索における核心的な課題は以下の通りです。

- **どの道が成功するか分からない**ため、同時に複数を探索しなければならない。
- **すべてを残すことはできない**。さもなければ情報の海に溺れてしまう。
- **成功したパスはメインラインにマージする必要がある**。さもなければ完全な解決策にならない。

管理メカニズムが欠けていると、次のようになります。
- パスを安全に捨てられない（誤って消すのが怖い）。
- パスを簡単にマージできない（コードの乖離）。
- パスを明確に比較できない（条件の不一致）。

## 核心的なメカニズム：隔離 ＋ 破棄可能性 ＋ 比較可能性

### メカニズム1：すべてのパスを隔離する

**隔離の3要素**：

1.  **独立した Git ブランチ**
    ```text
    exp/path-A-attention      # パス A：アテンションの改善
    exp/path-B-lr-schedule    # パス B：学習率の最適化
    exp/path-C-data-aug       # パス C：データオーグメンテーション
    exp/path-D-loss-combo     # パス D：損失の組み合わせ
    ```
    利点：
    - コードの変更が相互に独立しており、衝突しない。
    - いつでも切り替え、比較、マージができる。
    - Git の履歴に、各パスの進化が明確に記録される。

2.  **独立した設定ファイル**
    ```text
    configs/
      baseline.yaml              # 共通のベースライン
      path_A_attention.yaml      # パス A 用の設定
      path_B_lr_schedule.yaml    # パス B 用の設定
      path_C_data_aug.yaml       # パス C 用の設定
      path_D_loss_combo.yaml     # パス D 用の設定
    ```
    設定内で継承関係を明示する：
    ```yaml
    # path_A_attention.yaml
    base: baseline.yaml  # ベースライン設定を継承

    # 差分のみを記述
    model:
      attention_type: "multi_head"  # 変更点
      num_heads: 8

    experiment:
      name: "path_A_attention"
      hypothesis: "マルチヘッドアテンションはシングルヘッドより有効である"
    ```

3.  **独立した出力ディレクトリ**
    ```text
    outputs/
      path_A/
        2026-02-01_1030_baseline/
        2026-02-01_1500_multi_head_attn/
        2026-02-02_0900_improved_attn/
      path_B/
        2026-02-01_1100_baseline/
        2026-02-01_1600_cosine_schedule/
        2026-02-02_1000_warmup_schedule/
      path_C/
        ...
    ```
    利点：
    - 各パスの実験結果が明確にグループ化される。
    - パスを削除する際、対応するディレクトリを消すだけで済む。
    - アーカイブ時にパスごとにパッケージ化できる。

### メカニズム2：明確なライフサイクル管理

![パス管理](images/comics/08_path_management.png)

すべての探索パスは、明確なライフサイクルを持つべきです。

`作成 → 探索 → 評価 → 意思決定（維持 / アーカイブ / 削除）`

#### 作成フェーズ
```bash
# 1. ブランチの作成
git checkout main
git checkout -b exp/path-E-new-idea

# 2. 設定の作成
cp configs/baseline.yaml configs/path_E_new_idea.yaml
# 設定を編集し、仮説を記録する

# 3. 出力ディレクトリの作成
mkdir -p outputs/path_E/

# 4. パス情報の記録
cat > outputs/path_E/README.md <<EOF
# パス E：新しいアイデアの探索

## 仮説
[このパスで何を検証したいか？]

## ベースラインとの比較
比較対象：outputs/baseline/2026-02-01_1030_baseline
期待される改善：[どの程度の向上が見込まれるか？]

## 主要な変更点
- [変更 1]
- [変更 2]

#### 開始日
2026-02-05

#### 状態
探索中
EOF
```

#### 探索フェーズ
ブランチ上で自由にイテレーションを行い、各実験を記録します。
```bash
# 実験を実行
python train.py --config configs/path_E_new_idea.yaml \
                --output outputs/path_E/2026-02-05_1030_try1/

# 結果を記録（run.json は自動生成、run.md は手書き）
# 第6章参照
```

#### 評価フェーズ
定期的（例：毎週）にパスの価値を評価します。

**評価リスト**：
- **効果の評価**：
  - 最高結果：[指標]
  - ベースラインとの比較：[改善幅]
  - 安定性：[複数回実行時の分散]
- **コストの評価**：
  - 時間的コスト：[訓練時間はどの程度増えたか？]
  - 計算コスト：[追加のリソースが必要か？]
  - 複雑性のコスト：[コードの複雑度はどの程度増えたか？]
- **洞察と収穫**：
  - 何を発見したか？（成功しなかったとしても学んだことは何か？）
  - 失敗の原因：[なぜ期待を下回ったか？]
  - 副産物：[予期せぬ収穫はあったか？]
- **意思決定**：
  - [ ] 探索を続行する（深掘りする価値あり）
  - [ ] メインラインにマージする（成功）
  - [ ] アーカイブする（価値はあるが現在の最優先事項ではない）
  - [ ] 削除する（価値なし）

#### 意思決定フェーズ
評価結果に基づき、明確な意思決定を行います。

**意思決定 1：メインラインにマージ**（パスが成功した場合）
1.  **コードの整理**：変更を最小限にし、クリーンでテスト可能な状態にします。
2.  **完全な検証を実行**：
    `make test`
    `make reproduce RUN=path_E/best_result`
3.  **マージ**：
    ```bash
    git checkout main
    git merge exp/path-E-new-idea
    ```
4.  **タグ付け**：
    `git tag -a milestone-E-success -m "パス E 成功：新アイデアにより性能を X から Y に向上"`
5.  **ベースラインの更新**：
    `cp outputs/path_E/best_result outputs/baseline/`
6.  **実験ブランチの削除**：
    `git branch -d exp/path-E-new-idea`

**意思決定 2：アーカイブ**（価値はあるが、今すぐには使わない場合）
1.  **タグを打ってブランチの状態を保存**：
    `git tag -a archive/path-E-v1 -m "パス E アーカイブ：初期的な効果は確認されたが検証にさらに時間が必要"`
2.  **成果物の整理**：
    ```bash
    mkdir -p archives/path_E/
    cp -r outputs/path_E/ archives/path_E/
    cp configs/path_E_*.yaml archives/path_E/
    ```
3.  **まとめを書く**： `archives/path_E/SUMMARY.md`
4.  **ブランチの削除（タグは残す）**
5.  **outputs の削除（アーカイブ済みのため）**

**意思決定 3：削除**（価値がなかった場合）
1.  **最終確認**：価値のある発見やコードが本当にないか確認します。
2.  **出力と設定の削除**： `rm -rf outputs/path_E/`、`rm configs/path_E_*.yaml`
3.  **ブランチの削除**： `git branch -D exp/path-E-new-idea` (-D で強制削除)

### メカニズム3：公平な比較のためのベースライン

すべてのパスを比較する際、必ず **同一のベースライン** を使用しなければなりません。

#### ベースライン実験の確立
1.  **main ブランチでベースラインを実行**：
    `python train.py --config configs/baseline.yaml --output outputs/baseline/2026-02-01_1030_baseline/`
2.  **再現性を検証**：
    `make reproduce RUN=baseline/2026-02-01_1030_baseline`
3.  **タグ付け**：
    `git tag -a baseline-v1 -m "すべてのパスの共通ベースライン"`
4.  **ベースライン情報の記録**： `outputs/baseline/INFO.md` に設定、コミット、指標、用途、再現方法を記載します。

## 毎週のクリーンアップの儀式：実験の墓場の整理

**核心的な理念**：定期的なクリーンアップこそが、「ゴミの山」を避ける唯一の方法です。

### 毎週金曜午後のクリーンアップ・フロー（30分）

![08 09 weekly cleanup](images/comics/08_09_weekly_cleanup.png)

#### ステップ1：すべてのアクティブなパスをリストアップ（5分）
```bash
echo "アクティブな探索パス："
git branch | grep "exp/"
echo -e "\n出力ディレクトリのサイズ："
du -sh outputs/*/ | sort -rh
```

#### ステップ2：パスを一つずつ評価（15分）
各パスに対して3つの質問をします。
1.  **今週、進展はあったか？**
    - ある：維持。
    - ない：一時停止か、それとも破棄か？
2.  **ベースラインと比較して改善は見られるか？**
    - ある：マージの基準に達しているか？
    - ない：継続する価値があるか？
3.  **どれほどのリソースを占有しているか？**
    - ディレクトリサイズ、コードの複雑性、保守コスト。

#### ステップ3：クリーンアップの実行（10分）
古いパスのアーカイブ、不要な出力の削除、古い実験データの圧縮などを行います。

### 清掃の意思決定ツリー
各パスに対して判断します：
- 過去2週間以内に活動があったか？
  - はい → ベースラインより改善しているか？
    - 著しい改善 (>5%) → [メインへマージ]
    - わずかな改善 (3-5%) → [継続観察]
    - 改善なし (<3%) → [破棄を検討]
  - いいえ → アーカイブする価値があるか？
    - はい（ユニークな洞察がある）→ [アーカイブ]
    - いいえ → [削除]

## パスマージ戦略：探索から安定したメインへ

### マージ前のチェックリスト
`main` にマージする前に、以下を満たしていることを確認してください。
- [ ] ベースラインに対して安定した改善が見られる（複数回の実行で有効）。
- [ ] 変更が最小化されている（必要な修正のみが残っている）。
- [ ] コードがクリーンで保守可能（Lint とレビューに合格）。
- [ ] テストでカバーされている（最低限のスモークテスト）。
- [ ] 設定が明確に記録されている（再現可能）。
- [ ] 既存の機能を壊していない（回帰テストに合格）。
- [ ] ドキュメントが更新されている。

### 漸進的なマージ戦略
複雑なパスの場合は、一度にすべてをマージせず、段階的に行うことを推奨します。
例：パス A の「アテンション」「位置エンコーディング」「ハイパーパラメータ」を3つのステップに分けてマージし、各ステップでテストと検証を行います。これにより、問題の特定が容易になります。

## よくある質問と解決策

### Q1：パスが多すぎて覚えきれないときは？

**解決策**：パス追跡表（`docs/EXPLORATION_TRACKER.md`）を運用しましょう。
各パスの「状態」「仮説」「最高結果」「意思決定」「更新日」をテーブル形式で記録します。毎週5分この表を更新するだけで、すべてのパスの状態を明確に把握できます。

### Q2：異なるパス間でコードが衝突（コンフリクト）したときは？

**予防が最善の薬です**：
- パスごとに異なるモジュールを編集するようにする。
- 共有のコアコードは `src/` に置き、安易に変更しない。
- パス固有の変更は `experiments/` 内で行う。
**衝突した際**：
- 複数のパスを無理に一度にマージしない。
- まず一つをマージし、成功を確認した後で、新しい `main` に基づいて他のパスを作り直す。

### Q3：パスを消したあとで後悔したら？

**予防措置**：
- 削除前にタグを打つ： `git tag -a deleted/path-X`
- 削除前に短いまとめを書く。
- 重要なデータは安価なストレージ（クラウド等）にアーカイブしておく。

## 10分間アクション：現在の探索パスを整理する

今すぐできることが一つあるとすれば、現在のすべての探索パスをリストアップし、分類することです。

1.  **すべてのブランチと出力を書き出す**
    `git branch | grep "exp/"`
    `ls outputs/`

2.  **各パスを素早く分類する**
    「進行中」「アーカイブ」「削除期待」のいずれかに振り分け、仮説と現状をメモします。

3.  **一度クリーンアップを実行する**
    明らかに価値のないブランチや出力を削除し、活動していないが価値のあるパスをアーカイブ（タグ付け）します。

4.  **追跡表を作成する**
    `docs/EXPLORATION_TRACKER.md` を作成し、アクティブなパスを記録します。

5.  **来週のクリーンアップ時間を設定する**
    カレンダーに「毎週金曜 17:00 - 探索パスの整理（30分）」を追加しましょう。

この10分間のアクションを終えると、プロジェクトの状態に対するコントロール能力が向上し、どのパスを続け、どれを諦めるべきかが明確になります。「ゴミの山」への恐怖から解放されるはずです。

**覚えておいてください。マルチパス探索は研究に不可欠な要素ですが、管理されない探索は災厄に変わります。定期的なクリーンアップは負担ではなく、思考をクリアに保つための不可欠な儀式なのです。**
