# リポジトリ構造はあなたの第二の脳である

![插图](../images/03_code_repository.png)

研究コードの「混乱」は、能力不足から生じるのではなく、研究が本質的に並行した探索であることから生じます。同時に、複数の仮説、複数の実装、複数の実験エントリ、複数の出力、そして複数の図表を維持しなければなりません。

これらが構造化されずに積み上げられると、あなたの脳はインデックスとしての役割を強制されます：**「どのスクリプトがまだ動くのか？どの出力が信頼できるのか？どの変更が指標に影響を与えたのか？」**

リポジトリ構造の目的は見栄えではなく、**認知負荷を下げること**にあります。記憶に頼ることなく、「このコードは削除可能か、この出力は信頼できるか、このパスは再現可能か」を判断できるようにするためです。

## リアルな事例：場当たり的にコードを積み上げた代償

![从混乱到整洁](../images/comics/03_messy_to_clean.png)

私がAIコーディングアシスタントを使い始めたばかりの頃、このような教訓を得ました。あるアイデアを素早く検証するために、私はCopilotに「動く」コードを大量に生成させました。データ読み込み、モデル定義、トレーニングループ、評価スクリプトなど、数時間のうちに一見完全なフレームワークが出来上がりました。

### 初期段階の「成功」：

![03 04 early success](../images/comics/03_04_early_success.png)

コードは確かに動き、実験結果も出ました。私は興奮してイテレーションを続け、AIに新しい機能を次々と追加させました：データ拡張、異なるモデル変種、様々な評価指標……。変更のたびに「即効性」があり、コード量は急速に膨れ上がりました。

#### 崩壊の始まり：

![03 05 collapse begins](../images/comics/03_05_collapse_begins.png)

2週間後、論文用の対照実験を準備しようとしたとき、問題が表面化しました：

- どのスクリプトが最新で、どれが廃止されたものか分からなくなった。
- 同じデータ読み込みロジックが5つの異なるファイルにコピー＆ペーストされ、それぞれのバージョンが微妙に異なっていた。
- ベースラインと提案手法で異なる評価コードを使用していたため、結果が直接比較できなかった。
- 「非常に良い結果」を再現しようとしたが、その時に使用した設定やデータバージョンが見つからなかった。

#### 白紙からのやり直し：

![03 06 rewrite pain](../images/comics/03_06_rewrite_pain.png)

結局、私はすべての新しい実験を停止し、丸3日間かけて**ほぼすべてのコードを書き直す**ことになりました。この書き直しはAIが生成したコードにバグがあったからではなく、**構造が欠如していた**ためです。再利用可能なコアロジックと使い捨ての実験スクリプトが混在し、素早い試行錯誤のためのコードが整理らず、出力が各所に散らばって追跡不能になっていました。

この経験から、私は深く理解しました：AIはコードを素早く生成してくれますが、**構造のデザインは人間が行わなければならない**ということを。最初に「安定した部分」と「探索的な部分」を分離し、出力を run_id ごとに整理していれば、このような混乱に陥ることはなかったはずです。

#### ケーススタディの教訓：

このような問題は珍しいことではありません。AIを使って「動く」リポジトリを素早く構築したものの、再利用可能なコードと使い捨ての実験エントリを分離していない場合、よくある結末として、すべてのモジュールを書き直すことになり、AIが生成した断片はほぼすべて置換されることになります。**構造こそが、このような手戻りを防ぐための第一の防衛線です。**

## そのまま真似できるディレクトリ構造（研究向け）

![完美的目录结构](../images/comics/03_folder_tree.png)

    repo/
      src/                 # コアライブラリ：再利用可能、テスト可能、保守可能（慢变量）
      experiments/         # 実験エントリ：使い捨ての接着（glue）コード（快变量、破棄可能）
      configs/             # 統一設定：yaml/json（diff可能、追跡可能）
      data/                # ポインタや小規模サンプルのみ。大規模データは外部管理。
      outputs/             # 実行産物：run_id ごとに整理（整理/アーカイブ可能）
      reports/             # 論文図表と結論：outputsから自動生成
      scripts/             # データ準備/ダウンロード/評価などのツールスクリプト
      tests/               # 単体テスト + スモークテスト（品質の最低ライン）
      Makefile             # 共通エントリ：train/eval/reproduce/test
      README.md
      CLAUDE.md            # AIコーディングルール（推奨）

## 快変数と遅変数：「安定」を「探索」から分離する

![快慢变量分离](../images/comics/03_fast_slow_variables.png)

リポジトリ内の要素を二つのカテゴリーに分けることをお勧めします：

- **遅変数（stable）**：長期的に維持され、繰り返し再利用され、テストカバレッジが必要な部分。
- **快変数（explore）**：特定の仮説を素早く検証するためのエントリスクリプト、短命な接着コード、一回限りの分析。

本書の用語では、`src/` が遅変数であり、`experiments/` が快変数です。

**経験則**：探索は多少「汚く」ても構いませんが、コアライブラリは常に「清潔」であるべきです。探索は「速く」ても構いませんが、評価は常に「安定」していなければなりません。

### なぜこの分離がこれほど重要なのか？

私がコードを書き直した際に最も困ったのは、**「資産」と「消耗品」の区別がつかなかったこと**でした。すべてのコードが混ざっていると、間違って重要な機能を消してしまうのが怖くて何も削除できず、他の実験に影響が出るのが怖くて大胆な修正もできません。`src/` が資産であり、`experiments/` が消耗品であると明確に定義すれば、心理的な負担は大幅に軽減されます：

- `src/` への変更は慎重に行い、テストを必要とする。
- `experiments/` への変更は自由に行い、試し終わったら削除する。

## 各ディレクトリのDefinition of Done (DoD)

ディレクトリ名は、「何を置き、何を置かないか」が十分に明確であるときに初めて、混乱を劇的に減少させます。

### src/：コアライブラリ（再利用可能、テスト可能）

![03 07 src directory](../images/comics/03_07_src_directory.png)

- 再利用可能なモジュール：データ読み込み、モデルコンポーネント、損失関数、評価指標、共通ユーティリティを置きます。
- テスト可能であること：少なくとも重要なパスをカバーするスモークテストが必要です。
- ハードコーディング禁止：特定の実行（run）にのみ有効なパスやパラメータを含めてはいけません。

#### 反面教師：

私の書き直し事例では、元の「データ読み込み」コードに特定の実験のパスと前処理方法がハードコーディングされていたため、新しい実験の際、コピー＆ペーストして修正するしかありませんでした。最初からパスやパラメータを引数として渡すようにしていれば、この問題は起きませんでした。

### experiments/：実験エントリ（破棄可能）

![03 08 experiments directory](../images/comics/03_08_experiments_directory.png)

- 入口と接着コードのみを置く：**短命であることを許容し**、使い終わったら削除します。
- 価値が認められ、再利用されることが決まったロジックは、安定した時点で `src/` へ移行させます。

#### 実践的なアドバイス：

各実験スクリプトには日付や run_id で名前を付けます（例：`2026-02-01_baseline.py`）。これにより、どれが古い実験でどれが新しい実験かを一目で判断できます。1ヶ月以上経過し、価値がないと判断したスクリプトは定期的に（例えば毎週）整理しましょう。

### configs/：設定（追跡可能）

- 各「論文候補の結論」は、必ず一つのconfig（またはその追跡可能な生成方法）に対応している必要があります。
- configは最終的なパラメータに展開可能である必要があります（デフォルト値の乖離を防ぐため）。

### outputs/：産物（整理/アーカイブ可能）

- 実行によって生成された産物のみを置き、**必ず run_id ごとに**整理します。
- 上書き禁止：同じ run_id のディレクトリを再利用したり、手動で修正したりしてはいけません。
- 重要な産物はアーカイブする：長期ストレージに移動させ、リポジトリに巨大なバイナリを含めないようにします。

### reports/：図表と結論（再生成可能）

- 可能な限り、スクリプトで生成された図表・表と結論のドラフトのみを置きます。
- 論文の図表は、手動の作業を介さず `outputs/` から再生成できる必要があります。

### tests/：テスト（最低ラインを守る）

- 少なくとも1〜3分で終わるスモークテスト：データ読み込み $\rightarrow$ フォワードパス $\rightarrow$ 損失計算 $\rightarrow$ 評価までを一通り動かします。
- 重要な関数にはアサーション（断言）を入れる：shape、NaN、範囲、データリークの兆候などをチェックします。

## 入口の収束：「どう動かすか」を目立たせる

![03 09 makefile entry](../images/comics/03_09_makefile_entry.png)

研究における最も一般的な無駄は、他の人（未来の自分を含む）が「どうやって動かすか」を知らないことです。

すべての一般的な入口を `Makefile`（または同等のタスクランナー）に集約することをお勧めします：

- `make test`
- `make train CONFIG=...`
- `make eval RUN=...`
- `make reproduce RUN=...`

入口が十分に少なく、安定していれば、内部の複雑さを隠蔽し、外部に対して高い再現性を提供できます。

## 漸進的リファクタリング：混乱したプロジェクトから良好な構造への移行

すでに「混乱した」古いプロジェクトがある場合、一度にすべてをやり直そうとしてはいけません。以下は、段階的なリファクタリングのプロセスです：

### ステップ1：遅変数と快変数を特定し区別する

1.  **既存コードの精査**：プロジェクト全体をスキャンし、どのモジュールがコア機能（長期的に維持、繰り返し使用されるもの）で、どれが一回限りの実験スクリプトかをマークします。
2.  **ディレクトリの新設**：
    - `src/` を作成し、再利用が決まっているモジュールを移動させます。
    - `experiments/` を作成し、雑多な実行スクリプトや一時的なコードを移動させます。
3.  **大まかな階層化の完了**：このステップが終わるだけで、プロジェクト構造は明確になり始め、脳内のインデックス負荷が軽減されます。完璧を求めず、まずは明らかな部分を分けることから始めましょう。

### ステップ2：設定とパラメータの抽出

1.  **ハードコーディングの特定**：コードをスキャンし、ハードコーディングされた主要なパラメータ（学習率、バッチサイズ、パスなど）を見つけ出します。
2.  **設定ファイルの作成**：`configs/` ディレクトリにYAMLやJSONファイルを作成し、パラメータを一元管理します。
3.  **段階的な置換**：すべてのコードを一度に変更するのではなく、スクリプトを一回ずつリファクタリングし、正常に動作することを確認してから次に進みます。

#### 実践経験：

私のリファクタリング過程では、設定を抽出するステップだけで3つの隠れたバグが見つかりました：元のスクリプト間で「同じはずの」パラメータ値が実は異なっており、結果が比較不可能になっていたのです。

### ステップ3：出力パスの統一

1.  **ルールの策定**：`outputs/<run_id>/` という構造を使用することを決定します。
2.  **コードの修正**：すべての実験エントリを調整し、出力が run_id ごとにアーカイブされるようにします。
3.  **古い出力の整理**：散らばっていた古い出力ファイルを整理・アーカイブまたは削除し、outputs ディレクトリを清潔に保ちます。

### ステップ4：基本的なテストの追加

1.  **スモークテストの作成**：コアプロセスが動作することを検証する、1〜3分のクイックテストを作成します。
2.  **リファクタリングのたびに実行**：変更が基本機能を壊していないか確認します。
3.  **カバレッジの段階的拡大**：リファクタリングの進展に合わせて、重要な関数に単体テストを順次追加していきます。

#### 重要な原則：

一歩ずつ進むことが重要です。一度にすべてのリファクタリングを終わらせようとせず、各ステップで既存の機能が正常であることを確認しながら次に進んでください。私の書き直しには3日かかりましたが、最初から漸進的リファクタリングを採用していれば、通常の実験の合間に一週間かけて行え、進捗に影響を与えることもなかったでしょう。

## マルチタスク/マルチプロジェクトのディレクトリ階層管理

関連しているが独立した複数の研究タスクに直面した際、ディレクトリをどう組織するかは重要な問題です。

### 原則：独立したプロジェクトを優先する

**ベストプラクティス**：各研究プロジェクトで独立したコードリポジトリを使用します。これにより以下の利点があります：
- プロジェクト間の依存関係の競合を避ける。
- バージョン管理の独立性を確保する。
- 再現プロセスを簡素化する（各プロジェクトに独立した環境と依存関係がある）。

#### 経験則：
二つのプロジェクトで依存関係のバージョン、データセット、実行環境が大きく異なる場合、**リポジトリを分けることを強くお勧めします**。

### 単一リポジトリでのマルチプロジェクト階層構造

どうしても一つのリポジトリで複数の関連タスクを管理する必要がある場合（例：同一論文の複数の実験、または多くのコードを共有するサブプロジェクト）、以下の構造を採用できます：

    repo/
      projectA/
        src/
        experiments/
        configs/
        outputs/
        README.md
      projectB/
        src/
        experiments/
        configs/
        outputs/
        README.md
      common/
        src/               # プロジェクト間で共有される核心代码
        tests/             # 共有機能のテスト
        scripts/           # 共通ユーティリティスクリプト
      README.md            # 全体説明
      Makefile             # プロジェクト横断的な共通コマンド

### 命名規則と環境の分離

- **設定ファイルの命名**：プロジェクトのプレフィックスを使用します（例：`configs/projectA_baseline.yaml`, `configs/projectB_ablation.yaml`）。
- **出力ディレクトリ**：各プロジェクトのサブディレクトリ内で出力を管理するか、ルートディレクトリに統一しつつプロジェクト名をプレフィックスにします：`outputs/projectA/<run_id>/`。
- **環境管理**：コードが一つのリポジトリにあっても、依存関係の競合を防ぐために、プロジェクトごとに独立した仮想環境やDockerコンテナを維持することをお勧めします。

### いつコードを共有し、いつコピーすべきか

**common/ へコードを共有するタイミング**：
- 複数のプロジェクトで使用される基礎的なユーティリティ関数。
- 共通のデータ読み込みや前処理ロジック。
- 標準化された評価指標の計算。

**コードをコピーするタイミング**：
- コードがまだ急速に変化しており、プロジェクトごとにニーズが分かれる可能性がある。
- 共有によって過度な結合が生じ、独立性が損なわれる。
- プロジェクトが間もなく終了し、将来的に同期更新の必要がない。

#### 実践的なアドバイス：
最初はあえてコピーし、コードが本当に安定し、共有が確実に必要であると確信できた時点で common/ へ抽出するようにしましょう。早すぎる抽象化は共有コードの頻繁な修正を招き、かえって保守の負担を増やします。

## クイックスタート：AIを使ってリポジトリテンプレートを生成する

このプロセスをスピードアップするために、指導教員はあなたにAIアシスタントを使うことを勧めます。必要なディレクトリ構造とファイルを簡単に説明してください。例えば、Claudeに一文だけ書きます：

> "標準的な研究プロジェクトテンプレートを生成してください。ディレクトリは：src/、experiments/、configs/、outputs/、data/、reports/、scripts/、tests/。各ディレクトリの説明コメント付きで、README.mdで各ディレクトリの用途を説明し、test、train、eval、reproduceターゲットを含むMakefileも生成してください。"

わずか1分で、完全なプロジェクト構造とすべての基礎ファイルが生成されます。まだ一行のコードも書いていないのに、堅実な基礎ができています。これこそが「巨人の肩に乗る」ということです。今後、すべての新しいプロジェクトをこのような方法で始めることを決めました。

### 自分がこの「なぜ」を理解するために

AIボイラープレート生成を使うことは怠惰ではなく、**構造的な知恵**です。退屈なテンプレート作成をAIに外注することで、すべてのプロジェクトが最初からベストプラクティスを従うことを保証します。人間の努力は、輪の再発明ではなく、独特の科学問題に集中できます。

## 10分アクション：現在のプロジェクトを「一度だけ層分け」してみる

もし今すぐ一つだけ行うなら：現在のリポジトリを遅変数と快変数にざっくり分けてみてください。

1.  `src/` を作成し、再利用が決まっているモジュールを移動させる。
2.  `experiments/` を作成し、すべての入口スクリプトを移動させ、それらが短命であることを許容する。
3.  `configs/` を作成し、主要なパラメータをスクリプトから抽出する。
4.  出力を `outputs/<run_id>/` に統一することを決める。

すぐに「制御可能性」が向上したことを感じるはずです。何が資産で、何が使い捨ての消耗品であるかを区別し始めたからです。

### 個人の経験から：

もし私がAIコーディングアシスタントを使い始めたときにこの構造を確立していれば、あの3日間の書き直し作業は完全に回避できたはずです。良好な構造は見た目のためではなく、**あなたの脳がすべての詳細を記憶することを強いるのをやめ**、リポジトリ自体を信頼できる「第二の脳」にするためにあるのです。
