# プロジェクトの最小単位は「コード」ではなく「実験」である

![插图](images/02_experiment_flowchart.png)

研究プロジェクトにおいて、最小単位を「コード」と理解してしまうと、自然とGitですべてを管理しようとする傾向が強まります：コミット(commit)、ブランチ(branch)、マージ(merge)、ロールバック(rollback)などです。この習慣はエンジニアリング開発では非常に効果的ですが、研究業務においてはしばしば機能しなくなります。その理由は、研究の最終的な成果はコードそのものではなく、検証可能な結論や発見だからです。言い換えれば、コードは研究の結論に至るための手段の一つに過ぎず、実験結果こそが私たちが真に重視する成果なのです。

結論は実験から得られます。一つの実験は、追跡可能な一連の入力条件によって動かされ、再確認可能な出力結果を生み出します。したがって、本書では「実験」をプロジェクト操作の最小単位と定義し、それを中心にディレクトリ構造、ログ記録、自動化プロセス、および受け入れ基準を構築します。実験を基本単位とみなすことで、すべての結果に根拠があることを保証し、研究の再現性と信頼性を向上させることができます。

## 実験の定義：「何かを変えた」を比較可能なオブジェクトに変換する

簡単に言えば、**一つの実験 = コードバージョン + 設定 + データバージョン + 環境 + 出力 + 指標** です。より分かりやすく表現するなら、**「いかなる実行結果も、『それは一体どのようにして得られたのか？』という問いに答えられなければならない」**ということです。言い換えれば、コードや設定に「何か変更」を加えて結果を出したとき、その実行は独立した、比較可能な実験オブジェクトとして形成されるべきです。

### 答えなければならない6つの質問

![六个关键问题](images/comics/02_six_questions.png)

実験結果の追跡可能性と比較可能性を保証するために、各実験は少なくとも以下の6つの重要な質問に答えられる必要があります：

1.  **どのコードを使用したか？** -- コードバージョン（Gitのコミットハッシュなど）と、その時のコードベースに未コミットの変更（dirty）があったかどうかを明示します。これにより、どの版のコードで実験を行ったかが確実になります。

2.  **どの設定を使用したか？** -- 使用した設定パラメータのセット（設定ファイルのパスや、展開後の最終的なパラメータ値など）を明示します。設定は実験のハイパーパラメータや実行オプションを決定するため、明確に記録する必要があります。

3.  **どのデータを使用したか？** -- 使用したデータセットのバージョンやハッシュ、およびデータの分割方法（訓練/検証/测试集划分）を明示します。データの違いは結果に直結するため、データのソースとバージョンを正確に記述する必要があります。理想的には、データのハッシュやマニフェストファイル（manifest）を通じて一貫性を証明できるようにします。

4.  **どの環境を使用したか？** -- Pythonのバージョン、依存ライブラリのバージョン、ドライバのバージョン、および主要なハードウェア構成（CPU/GPUのモデルなど）といった実行環境の情報を記述します。環境の差異は再現性に影響を与える可能性があるため、他の誰かが別の環境で再実行する場合、元の環境を知る必要があります。

5.  **出力はどこにあるか？** -- 実験で生成された各種ファイル（モデルの重み、ログ、予測结果、キャッシュされた中間特征など）の場所を明確に記録します。成果物はその後の分析や検証の基礎となるため、保存され、見つけられる状態でなければなりません。

6.  **指标は何か、どのように計算されたか？** -- 実験の評価に使用された指标とその計算方法（评估脚本和任何后处理的细节を含む）を提示します。評価指标の計算定義が異なると結果を比較できなくなるため、透明で一貫した定義を保証する必要があります。

これら6つの要素はどれも欠かすことができません。もし一つでも答えられない質問があれば、その実験は完全な再現性がなく、得られた結論も説得力に欠けるものとなります。これらすべてを満たして初めて、「今回の結果がどうやって得られたのか」を理解していると言え、後日、正確に再現したり異なる実験と比較したりすることが可能になります。

#### 事例：AIが「一見完璧」だが動かないコードを生成した場合

![代码版本](images/comics/02_04_code_version.png)

言語をまたぐ移行（「コード翻訳」）のシナリオでは、APIのハルシネーション（幻覚）がよく発生します。モデルが生成した関数は一見合理的ですが、実際にはターゲット言語のライブラリに存在せず、生成されたコードがそのままでは動かないという状況です。結局、研究者はファイル一つ一つを書き直して修正する羽目になります。もしプロジェクトの最小単位を「コード」と誤解していれば、いくつのファイルや行数が生成されたかという罠に陥るかもしれません。しかし、「実験」を最小単位とする意義は、受け入れ基準が何個のファイルを生成したかではなく、**動く成果物と、対照評価可能な指標**を生み出したかにあるという点にあります。つまり、実験の成功は数行のコード変更ではなく、実行可能なモデルや結果が得られたか、そしてその変更の効果を証明する明確な評価指標があるかによって決まります。

## 実験オブジェクトモデル：研究プロセスを安定した「5要素」に分解する

![组装实验](images/comics/02_experiment_assembly.png)

研究ワークフローの各段階を明確に制御し、組み合わせやすく、かつツールの自動化を容易にするために、固定された概念オブジェクトのセットを用いて実験プロセスを記述できます。各実験は以下の5種類のオブジェクトに関連付けられます：

- **config（設定）**：一回の実行におけるすべての重要なパラメータ設定。保存や記録のためにシリアル化可能（YAML/JSONなど）であり、デフォルト設定の上書き（オーバーライド）をサポートし、差異（diff）を簡単に比較できる必要があります。configは実験をどう動かすか（モデルアーキテクチャ、学習率、エポック数など）を定義する、実験の設計図です。

- **dataset（データセット）**：使用されるデータのバージョンと分割方法。データセットオブジェクトは、バージョン番号、データハッシュ、またはマニフェストファイルなどを通じて使用データを明確に識別し、データの一貫性を証明する必要があります。これにより、異なる実験で同じデータ基盤を使用しているか、あるいはデータの差異を正確に知ることができます。

- **run（実行）**：具体的な一回のコード実行プロセス。runは通常、一意の実行ID (run_id)、タイムスタンプ、使用したコードのコミットバージョン、対応するconfig、乱数シード(seed)、および実行ログなどの情報を記録します。runは実際に発生した実験プロセスを表し、設定とコードを実践して結果を得る過程の記録です。

- **artifact（成果物）**：一回のrunによって生成されたすべての成果ファイル。例えば、学習済みのモデルの重み、テストセットに対する予測結果、キャッシュされた中間特徴量、評価時に生成された中間データなどがartifactです。artifactは実験の直接的な出力であり、その後の分析、比較、レポートはすべてこれらの成果物に基づきます。artifactを保存することで、時間のかかる計算を繰り返すことなく、いつでも実験結果を検証したり再利用したりできます。

- **report（レポート）**：人間が読むための要約。実験から得られた図表、表、主要な結論、および失敗ケースの分析などが含まれます。reportは定量的な実験結果を定性的な洞察に変換するものと言え、複数のrunの指標やartifactをまとめ、読者や意思決定者に提供します。これは実験成果の最終的な表現形式です。

これらのオブジェクト間の関係は次の一文で要約できます：

> config + dataset + env（環境）がコード実行を経て一つの run を生成し、その run がいくつかの artifact を出力する。artifact と指標計算结果に基づき、私たちは report を作成する。

このオブジェクトモデルを通じて、複雑な研究プロセスをいくつかの安定した「名詞」としてのオブジェクトに分解でき、思考やコミュニケーションが容易になります。例えば、実験について議論する際、「今回の実験にはどのconfigとdatasetを使ったか」、「どのようなartifactが生成されたか」、「最終的なレポートはどう書くか」などを明確に区別できます。さらに重要なのは、この区分がその後のツール化の基礎となることです。各オブジェクトに仕様（例：configはYAMLファイルで管理、artifactは特定のディレクトリに保存）を定めることで、実験ワークフローの標準化と自動化を実現できます。

## run_id：すべての実行を明確に指し示せるようにする

![实验命名](images/comics/02_run_id_naming.png)

論文やレポートを書く際、特定の条件下で実行された結果を頻繁に引用する必要があるでしょう。例えば、「ある設定で実行した際、最良の結果は……」といった具合です。もしその実験に安定した明確な名前がなければ、記述が非常に曖昧になり、読者の理解を妨げたり、異なる実験を混同したりしやすくなります。これを避けるために、毎回の実行に対して一意の run_id を生成し、そのIDを読みやすく、かつ時系列順になるようにすることをお勧めします。

実用的な方法は、タイムスタンプと短い説明を組み合わせることで、順序性があり分かりやすい命名を行うことです。例えば、日付と開始時間に、実験内容の簡潔な説明を加えます：

    2026-02-01_0930_baseline          （2026年02月01日09:30に開始されたベースライン実験）
    2026-02-01_1130_ablation_noaug    （2026年02月01日11:30に開始された消融実験 - データ拡張なし）
    2026-02-02_0045_sweep_lr3e-4      （2026年02月02日00:45に開始されたハイパーパラメータ探索 - 学習率3e-4）

このような命名規則により、ファイルが辞書順（＝時系列順）に並び、前後関係や大まかな内容を一目で把握できます。各 run_id は一意性と可読性を保証し、"experiment1", "experiment2" のような曖昧で比較不可能な名前を避けることができます。

ファイル構成としては、run_id をディレクトリ名とし、その中にその実験のすべての出力を集約して保存します。例：

    outputs/<run_id>/
        run.json        # この実行に関するメタ情報（代码版本、开始时间、参数配置等）
        run.md          # オプション：この実行に関する記述、观察和初步结论のログ
        metrics.json    # この実験の各種指標結果
        artifacts/      # この run で生成されたモデルや予測結果などを含むサブフォルダ

この構造により、実験結果の管理や照会が容易になります。例えば、複数の実験を比較したい場合、対応する run_id ディレクトリ内の metrics.json を直接開いて指標を確認したり、artifacts 内のモデルをロードして分析したりできます。

### 「final」の混乱を避ける：

![避免final混乱](images/comics/02_08_final_chaos.png)

実験の命名に「final（最終）」という言葉を使いたがる人は多いですが、「実験_final」を終えた後に少し改善が必要だと気づき、「実験_final_v2」やさらには「final_final」が生まれることがよくあります。最終的にどれが本当の最終結果か分からなくなり、混乱と誤解を招きます。これは典型的な命名規則の欠如による問題です。run_id を採用すれば、このような曖昧な呼称に頼る必要はなく、明確な時間と内容の記述ですべての試行を識別できます。どの実験を最終的な結果として採用するかは、レポートの中でどの run_id を使用したかを明記すればよいだけです。「final」という言葉に実験管理を邪魔されないようにしましょう。統一された命名ルールにより、各実験には根拠があり、何度目の試行かも明確で、二度と混同することはありません。

## 一つの実用的な原則：「比較可能性」を最優先事項とする

研究において、進捗の速さを決定するのは、モデルの学習にかかる物理的な時間ではなく、実験間の比較可能性の欠如による手戻りや疑問である場合が多いです。異なる実験の条件が一貫していなければ、たとえ数字が出たとしても、その差異がどこから来たのかを判断するのは難しく、結果的にやり直しを余儀なくされることさえあります。よくある反面教師には以下のようなものがあります：

- **評価基準の不一致**： ベースライン(baseline)と提案手法で異なる評価スクリプトを使用してしまい、指標の算出方法が異なり、直接比較できない。これにより、両手法を同一の基準で再評価するために余分な時間を費やすことになります。

- **後処理方法の不一致**： 実験Aと実験Bで異なる結果の後処理やフィルタリング戦略を採用したため、評価指標が同じ尺度ではなくなる。例えば、一方にはしきい値によるフィルタリングを適用し、もう一方には適用していない場合、統一しなければどちらが優れているか判断できません。

- **データ分割の不一致**： 実験Bで一時的にデータセットや分割方法を変更したが記録されておらず、実験Aと比較したときに実は不公平である場合。Bがより簡単なテストセットを使っているのに手法が優れていると主張しても、比較が同一基準でないため、結果に意味がありません。

これらの理由から、私たちは常に以下のことを心に留めておくべきです：**「いかなる重要な結論も、同一の評価パイプラインから得られ、実験間の比較可能性が保証されていなければならない」**。つまり、二つの実験結果を比較する際、意図的に変更した変数（モデル構造、ハイパーパラメータなど）を除いて、データ、評価基準、後处理方法、乱数シードなどのすべての要素は、可能な限り一致させるか、少なくとも追跡可能であるべきです。不一致が見つかった場合は、新しい実験で修正してやり直すか、レポートで差異を明確にし、直接の比較を避けるべきです。

比較可能性を最優先にすると、実験設計時により多くの注意を払い、各条件を揃える手間がかかるかもしれません。しかし、そうすることで不公平な比較による再試行や議論を避けられるため、結果的に研究の全体的なスピードは上がります。一つの実験から得られた結論が、真に揺るぎないものになるからです。

本章開始より、ディレクトリ構造、Gitワークフロー、DoD（完成の定義）、ログ記録、AI支援ワークフローなど、すべての章は「実験の追跡可能性」と「結果の対照可能性」という二つの中心的な目標を実現するために展開されます。本章で確立された理念は、研究管理のメソドロジー全体を貫くことになります。
