# AIコーディングアシスタントの導入に伴い、ワークフローをアップグレードせよ

![イラスト](images/07_ai_collaboration.png)


## イントロダクション：AIが「加速器」から「地雷製造機」に変わるとき

![AIアシスタント](images/comics/07_ai_sidekick.png)

あなたはGitHub Copilotの助けを借りて、1ヶ月で複雑なマルチモーダル学習フレームワークを構築し終えました。コードの生成速度は驚異的でした。以前は1日に200行書くのが精一杯でしたが、今は半日で500行書けます。自分の生産性が数倍になったと感じていました。

しかし、論文執筆の1週間前になって、問題が一気に噴出しました。

### 問題1：隠れたバグ

![07 05 hidden bug](images/comics/07_05_hidden_bug.png)

境界条件をテストしていたとき、モデルが `NaN` を出力していることに気づきました。コードを遡ると、データの前処理関数に問題がありました。稀なケースでゼロ除算が発生していたのです。この関数はCopilotが生成したもので、あなたは当時「動くこと」だけを確認し、境界条件を詳しく精査していませんでした。

### 問題2：不一致な実装

訓練時と評価時でデータオーグメンテーションの実装が異なっていたことが判明しました。訓練にはCopilotが生成したバージョンAを使い、評価には後であなたが手書きしたバージョンBを使っていたのです。両者の正規化手法に微妙な差異があり、訓練とテストの分布が不一致になった結果、パフォーマンスに悪影響を及ぼしていました。

### 問題3：過度に複雑なアーキテクチャ

「エレガント」に見せようと、Copilotに高度に抽象化されたアーキテクチャを設計させました。多くの抽象クラスやファクトリーパターンが導入されました。しかし今、機能を一つ修正しようとすると、ロジックが各抽象レイヤーに分散しているため、5つのファイルを書き換えなければならないことに気づきました。

### 問題4：検証の欠如

![AIコードの検証](images/comics/07_verify_ai_code.png)

Copilotが生成したコードの多くにテストが欠けていることに思い至りました。「エラーが出ずに実行できればいい」と考えていたため、境界条件、エラー処理、データの一貫性を系統的に検証したことがありませんでした。今からテストを追加しようとしても、コードの結合度が高すぎて単体テストが困難な状態でした。

#### 悔恨の瞬間

あなたはすべての新機能開発をストップし、1週間かけて以下の作業を行う羽目になりました。

- すべてのAI生成コードをレビューし、隠れた問題を見つけ出す。
- 不一致な実装を統一する。
- 過剰設計されたアーキテクチャを簡素化する。
- 欠落していたテストと検証を追加する。

あなたは気づきました。**「AIコーディングアシスタントが悪いのではなく、自分のワークフローが時代遅れだったのだ」**ということに。

AIを導入する前は、コード量が少なくエラーも少なかったため、記憶と経験だけで品質を管理できました。しかし、今はコード量が爆発的に増えています。それなのに検証メカニズムが「手作業のレビュー」のままでは、そのギャップは広がる一方です。

## AIコーディングの3大落とし穴

![AIの落とし穴](images/comics/07_ai_danger.png)

### 落とし穴1：生成速度が検証能力を上回る

**症状**：AIが1分間に100行のコードを生成し、あなたは「パッと見、良さそう」と受け入れます。しかし、境界条件、エラー処理、パフォーマンスへの影響などは精査されていません。

**結果**：
- 大量の隠れたバグが埋め込まれ、肝心な場面で露呈する。
- 「動くが堅牢ではない」実装がコードベースを埋め尽くす。
- リファクタリングのコストが、最初から正しく書くコストを大幅に上回る。

**本質的な問題**：検証メカニズムがアップグレードされず、「手作業によるレビュー」にとどまっている。

### 落とし穴2：再生成による不一致

**症状**：似たような機能が必要になったとき、既存のコードを再利用するのではなく、AIにもう一度生成させます。その結果、プロジェクト内に「似ているが微妙に異なる」実装が複数存在することになります。

**結果**：
- 一つのロジックを修正するために複数箇所を書き換える必要があり、修正漏れが発生しやすい。
- 異なる実装間の微妙な差異が、結果の不一致を招く。
- コードベースが肥大化し、保守コストが激増する。

**本質的な問題**： 「コアライブラリ・コード」と「使い捨てのグルー（接着剤）・コード」を区別できていない（第3章参照）。

### 落とし穴3：「ついでに修正」への過度な依存

**症状**：AIにある機能を実装させている最中に、「ついでにここも直して」「あそこも最適化して」と頼んでしまいます。一つのコミットに数十個のファイルの変更が含まれることになります。

**結果**：
- どの変更が問題を引き起こしたのか特定できなくなる。
- ロールバックしようとしても、あちこちに影響が及んでいて困難。
- コードの履歴が混乱し、ロジックの進化を追跡できなくなる。

**本質的な問題**：変更が「検証可能な最小単位」ではなくなっている（第1章参照）。

## アップグレードされたワークフロー：AIを「迅速に試行錯誤するジュニアプログラマー」と見なす

**核心的な理念**：AIはアシスタントであり、代替品ではありません。その強みは初期案を素早く生成することにあり、あなたの責任はそれを検証・統合・管理することにあります。

AIコーディングを2つのフェーズに分けて考えます。

1.  **生成フェーズ**：AIが初期案を素早く出力する（高速、荒削り、不完全さを許容）。
2.  **検証フェーズ**：人間がレビューし、テストし、リファクタリングする（低速、厳格、品質を保証）。

**重要な原則**：生成は速く、しかし統合は慎重に。

### 原則1：一度の変更は検証可能な最小単位にする

**具体的なアドバイス**：
- 一度にAIに生成させるコードの差分 (diff) は200行以内に抑える。
- 一度の変更は、一つのロジック機能（例：「データオーグメンテーションの追加」「NaNバグの修正」）に絞る。
- 変更は独立して検証可能（対応するテストや実験がある）でなければならない。

**実践例**：

❌ **悪い例**：
一つの変更に以下がすべて含まれている：
- データロード・ロジックの変更
- 新しいモデル層の追加
- 訓練ハイパーパラメータの調整
- 評価コードのリファクタリング
- 設定ファイルの更新
結果：もし実験結果が悪化しても、どの変更が原因か特定できません。

✅ **良い例**：
- **変更1 (独立したコミット)**：
  - データロード・ロジックの修正
  - テスト：データロードが通り、出力の形状 (shape) が正しいことを確認。
- **変更2 (独立したコミット)**：
  - 新しいモデル層の追加
  - テスト：モデルの順伝播 (forward) テストに合格。
- **変更3 (独立したコミット)**：
  - 実験を実行し、新モデルとベースラインを比較。
  - 記録：`run_id`、指標、結論。

### 原則2：常に「どのように検証するか」をセットにする

**具体的なアドバイス**：
AIにコードを生成させるとき、同時に検証用のコードも生成させるように要求します。

**プロンプト例**：
「データオーグメンテーション機能を実装してください。以下の内容を含めてください：
1. 実装コード
2. 単体テスト（正常系と境界系の両方をカバー）
3. 使用例
4. 考えられるリスク」

**検証リスト（変更ごとのチェックポイント）**：
- [ ] コードが実行可能である（クラッシュしない）。
- [ ] 出力が期待通りである（shape、数値範囲、データ型）。
- [ ] 境界条件が正しく処理されている（空の入力、極端な値、不正な入力）。
- [ ] 既存機能に影響を与えていない（回帰テストに合格）。
- [ ] テストでカバーされている（最低限のスモークテスト）。

### 原則3：「ついでに広範囲をリファクタリング」することを禁止する

**症状の特定**：
⚠ **危険信号**：
- AIの提案：「ついでにこの部分をリファクタリングして、もっとエレガントにしておきますね」
- あなたの考え：「どうせ変えるんだし、一緒にやってもらおう」
- 結果：一つのPRに機能追加、リファクタリング、バグ修正が混在する。

**正しいやり方**：
1.  **機能を先に実装し、リファクタリングは後で行う**：
    ```bash
    # ステップ1: 機能を実装（荒削りで可）
    git commit -m "feat: add data augmentation (rough version)"

    # ステップ2: 機能の正しさを検証
    pytest tests/test_data_aug.py

    # ステップ3: 独立してリファクタリング（機能は変えない）
    git commit -m "refactor: clean up data augmentation code"

    # ステップ4: リファクタリングによって機能が壊れていないか検証
    pytest tests/test_data_aug.py
    ```
2.  **リファクタリングと機能を分離する**：
    - 機能変更：コミットメッセージに `feat:` または `fix:` を使う。
    - リファクタリング：コミットメッセージに `refactor:` を使う。
    - 決して混ぜない。

### 原则4：コアロジックは必ず人間がレビューする

**「コアロジック」の定義**：
以下のコードをAI任せにしてはいけません。必ず人間が詳細に精査してください。

- **データ処理**：ロード、前処理、分割、オーグメンテーション。
- **モデルの核心**：損失関数、重要なモジュール（Attention、正規化など）。
- **評価ロジック**：指標の計算、後処理、スレッショルド（閾値）の選択。
- **ランダム性の管理**：乱数シードの設定、ランダムサンプリングのロジック。
- **ハイパーパラメータ**：学習率スケジューリング、重み減衰、ドロップアウト率。

**レビューリスト**：
- ロジックの正確性（アルゴリズムの実装は正しいか？）。
- 境界条件（データが空だったり極端な値だったりしたときにどうなるか？）。
- データの一貫性（訓練とテストのロジックは一致しているか？）。
- ランダム性（シード設定は正しいか？ 再現可能か？）。
- パフォーマンスへの影響（極端に遅くならないか？ メモリを使い切らないか？）。

### 原則5：最小限のテストを先に追加してから、コアロジックを変更する

**アンチパターン**：
あなた：Copilot、このデータロード関数をリファクタリングして。
Copilot：[150行のコードを生成]
あなた：いいね、採用！
[1週間後、データロードに問題があることが判明。しかしすでに多くの実験を終えてしまっている]

**正しい流れ**：
```bash
# ステップ1: まず現在のコードに対してテストを書く
def test_data_loader_current():
    """現在のデータロードの挙動をテスト"""
    loader = DataLoader(...)
    batch = next(iter(loader))

    assert batch['image'].shape == (32, 3, 224, 224)
    assert batch['label'].shape == (32,)
    assert batch['label'].min() >= 0
    assert batch['label'].max() < num_classes

# ステップ2: テストを実行し、合格することを確認
pytest tests/test_data_loader.py

# ステップ3: リファクタリングを行う
# [Copilotが新しいコードを生成]

# ステップ4: テストを実行し、挙動が変わっていないことを確認
pytest tests/test_data_loader.py

# ステップ5: テストが失敗した場合は、修正するかロールバックする
```

**テストファーストのメリット**：
- 現在の挙動を明確にできる（回帰テストの基準になる）。
- リファクタリングを迅速に検証できる（1時間の実験ではなく1分のテストで済む）。
- 既存機能を壊すことを防げる。
- 「正しい挙動とは何か」を強制的に考えさせられる。

## AIルールページ（CLAUDE.md）：チーム開発の合意形成

チーム内でAIの使用規範を統一するために、プロジェクトのルートディレクトリに `CLAUDE.md`（または `AI_RULES.md`）を作成し、AIコーディングの境界とプロセスを明確にすることを推奨します。

### CLAUDE.md テンプレート

```markdown
# AIコーディングアシスタント使用規範

本プロジェクトでは、AIコーディングアシスタント（GitHub Copilot、Claude、GPTなど）を開発の補助として使用します。
コードの品質と保守性を確保するため、AIが生成したすべてのコードは以下の規範に従う必要があります。

## 核心原則

1. **AIが生成し、人間が責任を持つ**：AIは下書きを素早く作成できますが、
   人間が必ずレビュー、テスト、管理を行わなければなりません。
2. **小さな歩みで進める**：一度の変更は差分200行以内に抑え、独立して検証
   可能でなければなりません。
3. **テストファースト**：コアロジックを変更する前にテストを追加し、変更後も
   テストに合格しなければなりません。
4. **「ついで」のリファクタリング禁止**：機能変更とリファクタリングは
   コミットを分ける必要があります。

## 操作規範

### 1. すべての変更に検証方法を付随させる

コミットメッセージやPR（プルリクエスト）の説明に以下を明記してください：

```text
検証方法：
- [ ] テスト実行：pytest tests/test_xxx.py
- [ ] 実験実行：python train.py --config xxx
- [ ] 出力の確認：出力のshapeが [B, C, H, W] であること
```

### 2. 変更ごとにリスクポイントを記録する

```text
潜在的なリスク：
- データ前処理を変更したため、データ分布に影響する可能性がある
- ランダムな操作を追加したため、シード設定の確認が必要
- 評価ロジックを変更したため、公平性を保つためにベースラインの再実行が必要
```

### 3. ロールバック戦略を準備する

```bash
ロールバック戦略：
- テストが失敗した場合：git checkout -- <ファイル名>
- 実験結果が悪化した場合：コミット `<hash>` まで戻す
- 他の機能に影響が出た場合：ロールバックし、新しいブランチで個別にデバッグ
```

## 禁止事項

[NO] **禁止1：機能追加とリファクタリングを混ぜる**
  - 機能変更とリファクタリングは別々のコミットにすること
  - 問題の特定とロールバックが容易になる

[NO] **禁止2：一度に多くのファイルを変更する**
  - 一度のコミットで5ファイルを超える変更は避けること（特殊な場合を除く）。
  - 多くのファイル変更が必要な場合は、複数のコミットに分割すること。

[NO] **禁止3：テストをスキップしてマージする**
  - `main` ブランチにマージする前に、すべてのテストに合格している必要がある。
  - 関連するテストがない場合は、先にテストを追加すること。

[NO] **禁止4：main ブランチで直接変更を加える**
  - AIが生成したすべてのコードは、まず実験用ブランチで検証すること。
  - 検証に合格してから `main` にマージすること。

## 推奨事項

[YES] **推奨1：コアロジックをテストでカバーする**
  - データロード、モデルの核心、評価ロジックには単体テストが必要です。
  - コアロジックを修正するたびに、テストが合格することを確認してください。

[YES] **推奨2：実験結果を比較可能にする**
  - 結果に影響を与える変更を加える際は、必ず比較実験を行ってください。
  - 変更前後の `run_id` と指標の比較を記録してください。

[YES] **推奨3：設定ファイルのバージョンを同期させる**
  - 結果に影響を与える変更を加える際は、対応する `config` を更新してください。
  - 設定ファイルはコミットし、タグを付けて保存してください。

[YES] **推奨4：ドキュメントを同時に更新する**
  - APIを変更した場合は、ドキュメントも更新してください。
  - 新機能を追加した場合は、READMEの使用説明を更新してください。

## 完了定義 (DoD)（main へのマージ前）

- [ ] 変更が200行以内である（または十分に議論されている）。
- [ ] すべてのテストに合格している。
- [ ] コアロジックを人間がレビュー済みである。
- [ ] 明確なコミットメッセージがある。
- [ ] 検証方法、リスクポイント、ロールバック戦略が記載されている。
- [ ] 実験結果に影響する場合、比較実験の記録がある。

## 実践例：AI支援の正しい活用方法

### ケース1：新しいモデルコンポーネントの追加

❌ **間違ったやり方**：
あなた：Copilot、マルチヘッドアテンションモジュールを実装して。
Copilot：[200行のコードを生成]
あなた：良さそう、採用！ そのまま訓練に投入しちゃおう。
[訓練がクラッシュ。アテンションの計算にバグがあることが判明]

✅ **正しいやり方**：
1. **下書きを生成させる**：
   あなた：Copilot、マルチヘッドアテンションモジュールを実装してください。以下を含めてください。
     - 実装コード
     - 単体テスト
     - 使用例
2. **人間がレビューする**：
   - softmaxの前に `sqrt(d_k)` で除算しているかチェック。
   - マスクの実装が正しいかチェック。
   - 出力の形状 (shape) が期待通りかチェック。
3. **テストを書く**：
   ```python
   def test_multi_head_attention():
       attn = MultiHeadAttention(d_model=512, n_heads=8)
       x = torch.randn(32, 100, 512)  # (batch, seq, dim)
       out, weights = attn(x, x, x)

       assert out.shape == (32, 100, 512)
       assert weights.shape == (32, 8, 100, 100)
       assert torch.allclose(weights.sum(dim=-1),
                             torch.ones_like(weights.sum(dim=-1)))
   ```
4. **モジュールを個別にテストする**：
   `pytest tests/test_attention.py -v`
5. **小規模なデータで統合テストを行う**：
   `python train.py --config configs/test_attention.yaml --data_subset 100 --epochs 2`
6. **問題ないことを確認してから本格的な訓練を開始する**：
   `python train.py --config configs/attention.yaml`

### ケース2：データロードのリファクタリング

❌ **間違ったやり方**：
あなた：このデータロードのコード、ぐちゃぐちゃだからCopilotにリファクタリングしてもらおう。
Copilot：[DataLoader クラスを丸ごと書き換え]
あなた：よし、新しいバージョンを使おう！
[実験をやり直すと結果が以前と一致しない。どこが間違ったのかわからない]

✅ **正しいやり方**：
1. **旧バージョンの挙動テストを書く**：
   ```python
   def test_old_data_loader_behavior():
       """旧バージョンの挙動を基準として記録"""
       loader = OldDataLoader(...)
       batch = next(iter(loader))

       # 重要な挙動を記録
       assert batch['image'].shape == (32, 3, 224, 224)
       assert batch['image'].dtype == torch.float32
       assert batch['image'].min() >= -1.0
       assert batch['image'].max() <= 1.0
       # ... さらにアサーションを追加
   ```
2. **テストを実行し、合格することを確認**：
   `pytest tests/test_data_loader.py::test_old_behavior -v`
3. **AIにリファクタリングさせる**：
   Copilot：[新しい DataLoader を生成]
4. **新バージョンに対しても同じテストを書く**：
   「新バージョンでも挙動が一致することを確認する」
5. **両バージョンの出力を直接比較する**：
   ```python
   def test_output_consistency():
       """新旧バージョンの出力を直接比較"""
       old_loader = OldDataLoader(seed=42)
       new_loader = NewDataLoader(seed=42)

       old_batch = next(iter(old_loader))
       new_batch = next(iter(new_loader))

       torch.testing.assert_close(old_batch['image'],
                                  new_batch['image'])
   ```
6. **一致していれば、フルスケールの実験で検証する**：
   `make reproduce RUN=baseline`（旧バージョンを使用）
   `make train CONFIG=configs/baseline_new_loader.yaml`（新バージョンを使用）
   結果を比較。

## よくある質問と解決策

### Q1：AIが生成したコードが複雑すぎて理解できないときは？

**解決策**：
- 受け入れを拒否しましょう！ AIにもっとシンプルなバージョンを再生成させます。
- **プロンプトのヒント**：
  「XXX機能を実装してください。以下の要件を守ってください：
  - 過度な抽象化を避け、シンプルで直接的なコードにすること。
  - 標準ライブラリと一般的なパターンを中心に使うこと。
  - 各ステップに詳細なコメントを付けること。」
- **教訓**：あなたが今理解できないコードは、未来のあなたも理解できませんし、ましてや他人はもっと理解できません。

### Q2：AI生成コードにバグがあり、直しても別のバグが出てくるときは？

**解決策**：
- AIに何度もバグ修正をさせて無限ループに陥るのはやめましょう。
- **正しいやり方**：
  1. まずテストを書き、バグを再現させる。
  2. 人間の手でバグを修正する（最小限の変更で）。
  3. テストに合格した後で、リファクタリングが必要か検討する。
- AIは問題のヒントをくれるかもしれませんが、最終的な修正は人間が行うべきです。

### Q3：チームメンバーがAI使用規範を守らないときは？

**解決策**：
- `git pre-commit hook` に自動チェックを組み込みます：
  ```bash
  # .git/hooks/pre-commit
  #!/bin/bash

  # コミット時の差分行数をチェック
  DIFF_LINES=$(git diff --cached | wc -l)
  if [ $DIFF_LINES -gt 400 ]; then
      echo "Error: commit diff too large ($DIFF_LINES lines)"
      echo "Please split into smaller commits"
      exit 1
  fi

  # テストがあるかチェック
  if git diff --cached --name-only | grep -q "src/"; then
      if ! git diff --cached --name-only | grep -q "tests/"; then
          echo "Warning: src/ を変更しましたが、tests/ に変更がありません。"
          echo "テストが更新されているか確認してください。"
      fi
  fi

  # テストの実行
  pytest tests/ -q || {
      echo "Error: tests failed"
      exit 1
  }
  ```
- CI（継続的インテグレーション）で強制的に実行します（次節参照）。
- コードレビュー時に厳格にチェックします。

## 10分間アクション：次のAIコーディングに向けたチェックポイントの設置

今すぐできることが一つあるとすれば、次のAI支援コーディングに備えて、最小限の検証プロセスを構築することです。

1.  **CLAUDE.md を作成する**
    本章のテンプレートをコピーして、プロジェクトのルートディレクトリに配置します。

2.  **スモークテストを書く**
    ```python
    # tests/test_smoke.py
    def test_basic_training_loop():
        """基本的な訓練プロセスが実行可能か確認"""
        config = load_config("configs/test.yaml")

        config["data_subset"] = 100

        model, metrics = train_model(config)

    ```

3.  **pre-commit hook を設定する**
    ```bash
    # シンプルなバージョン：テストを実行するだけ
    echo '#!/bin/bash\npytest tests/ -q' > .git/hooks/pre-commit
    chmod +x .git/hooks/pre-commit
    ```

4.  **一連のフローを試してみる**
    ```bash
    # 1. 実験用ブランチを作成
    git checkout -b exp/test-ai-workflow

    # 2. AIに小さな変更（ユーティリティ関数の追加など）をさせる
    # 3. 対応するテストを書く
    # 4. テストを実行する
    pytest tests/test_xxx.py

    # 5. コミット（hookが自動で走る）
    git add .
    git commit -m "feat: add utility function X"

    # 6. hookが通れば、main にマージ
    git checkout main
    git merge exp/test-ai-workflow
    ```

次にAIコーディングを行うときからは、**「生成 → レビュー → テスト → 検証 → マージ」** という流れがデフォルトの動作になるはずです。このプロセスが習慣化すれば、AIはあなたの地雷製造機ではなく、常に強力な加速器となってくれるでしょう。
