# 项目的最小单位不是\"代码\"，是\"实验\"

在科研项目中，如果你把最小单位理解成\"代码\"，自然会倾向于用 Git 来组织一切：提交(commit)、分支(branch)、合并(merge)、回滚(rollback) 等等。这种习惯在工程开发中非常有效，但在研究工作中往往失灵。原因在于：研究的最终产出并不是某段代码本身，而是一条可被验证的结论或发现。换言之，代码只是达到研究结论的手段之一，实验结果才是我们真正关心的成果。

结论来自实验。 一个实验由一组可追溯的输入条件驱动，产生出可复查的输出结果。因此，本书将\"实验\"定义为项目操作的最小单位，并围绕它来组织目录结构、日志记录、自动化流程以及验收标准。通过将实验视作基本单元，我们可以确保每一次结果都有据可循，提升研究的可重复性和可靠性。

## 实验的定义：把\"我改了点东西\"变成可比的对象

简单来说，**一个实验 = 代码版本 + 配置 + 数据版本 + 环境 + 输出 + 指标**。用更直白的话描述就是：**任何一次跑出来的结果，都必须能回答\"它到底是怎么来的？\"** 换言之，每当你对代码或配置\"改了点东西\"并跑出结果时，这次运行都应当形成一个独立的、可比较的实验对象。

### 必须能回答的 6 个问题

为了保证实验结果的可追溯和可比较，每次实验至少要能回答以下六个关键问题：

1.  **用的是什么代码？** -- 指明代码版本，例如 Git 的 commit hash，以及当时代码库是否有未提交修改（dirty）。这确保我们知道使用了哪一版代码跑的实验。

2.  **用的是什么配置？** -- 指明所用的配置参数集合，比如配置文件路径，以及解析展开后的最终参数值。配置决定了实验的超参数和运行选项，必须明确记录。

3.  **用的是什么数据？** -- 指明所用的数据集版本或哈希，以及数据的划分方式（训练/验证/测试集划分）。数据不同会直接影响结果，因此需要精确描述数据来源和版本。理想情况下，能通过数据的哈希或清单文件(manifest)证明数据的一致性。

4.  **用的是什么环境？** -- 描述运行所依赖的环境信息，例如 Python 版本、依赖库版本、驱动版本，以及关键硬件配置（CPU/GPU 型号等）。环境差异可能影响实验结果的重现，如果有人在另一环境重跑，需要知道原始环境是什么。

5.  **产出存在哪里？** -- 清晰记录实验产出的各类文件的位置，比如模型权重、日志、预测结果、缓存的中间特征等等。产出物是后续分析和验证的基础，必须保存并能够找到。

6.  **指标是什么，如何计算的？** -- 给出实验评估使用的指标及其计算方法，包括评估脚本和任何后处理的细节。不同的指标计算口径会导致结果不可比，必须保证指标定义透明、一致。

上述六个要素缺一不可。如果有任何一个问题无法回答，那么这次实验就不是完全可复现的，得出的结论也会缺乏说服力。只有同时满足这六点，我们才能说\"我们知道这次结果是怎么来的\"，也才能在日后精确重现或比较不同实验。

##### 案例：AI 生成\"看似完整\"的代码，但无法运行。

在跨语言迁移（\"代码翻译\"）的场景中，经常会出现 API 幻觉 的现象：模型生成的函数看起来很合理，但实际上根本不存在于目标语言的库中，导致生成的代码无法直接运行。最终研究人员不得不逐个文件进行重写修正（详见案例 [\[case:code_translation_hallucination\]](#case:code_translation_hallucination){reference-type="ref" reference="case:code_translation_hallucination"**）。如果我们把项目的最小单位误当成了\"代码\"，可能会陷入只关注生成了多少文件、多少行代码的陷阱。然而，将\"实验\"作为最小单位的意义在于：我们验收的标准不是产出了多少文件，而是产出了**可运行的成果，以及可对照评价的指标**。换句话说，一次实验是否成功，不取决于改动了几行代码，而取决于你是否得到了可执行的模型或结果，以及明确的评测指标来证明改动的效果。

## 实验对象模型：将研究过程拆解成稳定的\"五要素\"

为了让研究流程中的各环节都清晰可控、易于组合，并方便工具自动化，我们可以用一组固定的概念对象来描述实验过程的要素。每个实验都涉及以下五种对象：

- **config（配置）：**一次运行的所有关键参数设置。它应当是可序列化的（便于保存记录），支持局部覆盖的（便于在默认配置上修改)，并且可以方便地比较差异(diff)。config 定义了实验要怎么跑，比如模型架构参数、学习率、训练轮数等，是实验的蓝图。

- **dataset（数据集）：**所使用的数据版本以及划分方式。数据集对象应该明确标识所用的数据，如通过版本号、数据哈希或清单文件来证明数据的一致性。这样可以确保不同实验使用相同的数据基础，或清楚地知道数据差异。

- **run（运行）：**一次具体的代码执行过程。一个 run 通常会记录唯一的运行ID (run_id)、时间戳、所用代码的 commit 版本、对应的 config、随机种子(seed)以及运行日志等信息。run 表示一次真实发生的实验过程，是把配置和代码付诸实践得到结果的过程记录。

- **artifact（产出物）：**由一次 run 所生成的所有成果文件。例如训练得到的模型权重文件、模型对测试集的预测结果、缓存的中间特征、评估时生成的中间数据等等，都是 artifacts。artifact 是实验的直接输出，我们后续的分析、对比、报告都建立在这些产出物之上。保存 artifacts 能让我们随时检视或复用实验结果，而不必重复耗时的计算。

- **report（报告）：**面向人类阅读的总结性内容，包括从实验中得出的图表、表格、关键结论句，以及对失败情况的分析等。report 可以看作将定量的实验结果转化为定性的洞见，往往汇总了多个 run 的指标和artifact，提供给读者或决策者参考。它是实验成果的最终表达形式。

这些对象之间的关系可以用一句话来概括：

> config + dataset + env（环境）经过代码执行，生成一个 run；该 run 产出若干 artifact；基于 artifact 和指标计算结果，我们撰写出 report。

通过这种对象模型，我们将纷繁复杂的研究过程拆解成了几个稳定的\"名词\"对象，便于思考和沟通。例如，在讨论实验时，我们可以明确地区分\"这次实验用了哪个 config和 dataset\"、\"产生了哪些 artifact\"、\"最终报告怎么写\"等等。更重要的是，这种划分为后续的工具化打下基础------我们可以为每类对象制定规范（比如 config 用 YAML 文件管理，artifact 按照特定目录保存），实现实验流程的标准化和自动化。

## run_id：让每一次运行都可以被清晰指代

在撰写论文或报告时，你可能需要频繁引用某次特定设置下跑出的结果，例如：\"我们用某个设置跑出来的最好结果是......\"。如果这次实验没有一个稳定且清晰的名字，你在描述时就会非常含糊，不利于读者理解，也容易混淆不同实验。为避免这种情况，我们建议每次运行都生成一个唯一的 run_id，并尽量让这个 ID 可读且具备时间顺序。

一个实用的做法是将时间戳和简短描述结合，形成有序且易懂的命名。例如，可以按日期和启动时间命名，再加上对实验内容的简述：

    2026-02-01_0930_baseline          （2026年02月01日09:30启动的 baseline 实验）
    2026-02-01_1130_ablation_noaug    （2026年02月01日11:30启动的 消融实验-去掉数据增广）
    2026-02-02_0045_sweep_lr3e-4      （2026年02月02日00:45启动的 超参数网格实验-学习率3e-4）

这样的命名约定使得文件按字典序即是按时间顺序排列，一眼就能看出先后关系和大致内容。每个 run_id 都保证了唯一性和可读性，避免了\"experiment1\"、\"experiment2\"这类模糊且不可比较的名字。

在文件组织上，可以以 run_id 作为目录名，集中保存该次实验的所有输出。例如：

    outputs/<run_id>/
        run.json        # 关于此次运行的元信息（例如代码版本、启动时间、参数配置等）
        run.md          # 可选：记录对这次运行的描述、观察和初步结论的日志
        metrics.json    # 此次实验的各项指标结果
        artifacts/      # 子文件夹，内含该 run 产出的模型、预测结果等文件

通过这种结构，我们能够方便地管理和查询实验结果。例如，当你想比较多个实验时，可以直接打开对应 run_id 目录下的 metrics.json 查看指标，或载入 artifacts 中的模型进行分析。

##### 避免\"final\"混乱：

很多人在命名实验时喜欢用\"final\"（最终）字样，但经常出现的情况是做完\"实验_final\"之后又发现需要小改进，于是又有\"实验_final_v2\"乃至\"final_final\"。最后自己都搞不清哪个才是真正的最终结果，造成混乱和误解。这正是缺乏规范命名的典型问题。采用 run_id 的方案后，你不会再依赖这些含糊的称呼来标记最终成果，而是用清晰的时间和内容描述来标识每一次尝试。至于哪个实验是最终采纳的结果，可以在报告里明确指出使用哪个 run_id 即可。总之，不要再让\"final\"这样的字眼干扰你的实验管理；通过统一的运行命名，每次实验都有据可依，该第几次就是第几次，再也不会混淆。

## 一条实用原则：将\"可比性\"放在第一优先级

在研究中，决定进展快慢的往往不是模型训练所花的物理时间，而是由于实验之间缺乏可比性所导致的反复和疑惑。如果不同实验的条件不一致，那么哪怕结果数字出来了，你也很难判断差异源自何处，甚至可能因此推翻重做。常见的反面例子包括：

- **评价标准不一：** 基准方法 (baseline) 和你的新方法用了不同的评估脚本，导致结果度量口径不一样，无法直接比较。这会迫使你花额外时间将两者重新放到同一标准下评估。

- **后处理方式不一致：** 实验A和实验B各自用了不同的结果后处理或过滤策略，导致评估指标不在同一尺度上。比如一个结果用了额外的阈值筛选而另一个没有，如果不统一处理，你很难说清哪个方法更好。

- **数据划分不一致：** 实验B临时换了数据集或划分方式但没有记录，结果拿出来和实验A比较时其实不公平------可能B用了更简单的测试集却声称方法更优。这种情况下，即使结果好了也毫无意义，因为比较不在同一基准上。

由于上述种种原因，我们应当始终牢记：**任何重要的结论都必须来自同一条评估流水线，确保实验之间具有可比性**。也就是说，在比较两个实验的结果时，除了有意改变的那个变量（例如模型结构的不同、超参数的不同等），其他所有环节------数据、评估标准、后处理方法、随机种子等------都应尽可能保持一致或有据可查。一旦发现有不一致的地方，要么在新的实验中纠正过来重新跑，要么明确地在报告中说明不同之处并避免直接比较。

以可比性为第一优先级，可能会让你在设计实验时多花一些心思去对齐各项条件，但是这样做反而加速了整体研究进度。因为你避免了日后由于不公平比较带来的反复试验和争论，一次实验的结论就能真正站得住脚、经得起推敲。
