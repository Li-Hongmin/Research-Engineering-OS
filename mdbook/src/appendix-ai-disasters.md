# AI 助手引发的真实研发"灾难"案例（用于对照） {#app:ai_disasters**

本附录收集你提供的案例，并将它们抽象成可复用的工程教训。正文各章会穿插引用这些案例，作为"为什么要这样做"的现实证据。

## 案例 A：用 Copilot 开发整套应用，最终推倒重写 {#case:copilot_rewrite_all**

**现象：**几乎全靠 AI 产码快速搭起应用，但随后发现每个部分都需要重写，最后提交代码里几乎不剩 AI 片段。

**核心教训：**AI 让你更快到达"能跑"，但不自动带来"可维护/可演进"。如果缺少测试、架构边界与验收标准，返工会被放大。

## 案例 B：让 Copilot 包办代码库，反复返工且引入安全/逻辑隐患 {#case:copilot_overdelegation**

**现象：**AI 能高效生成样板代码，但也会自信地产生错误假设（数据库结构、函数存在性、框架边界），甚至引入安全隐患；并可能过度设计，导致代码臃肿。

**核心教训：**AI 是放大器：你越不理解系统，它越会帮你更快失败；你越理解边界与数据流，它越能替你省时间。

## 案例 C：模型输出格式变动导致工作流崩溃 {#case:format_shift_breaks_workflow**

**现象：**底层模型升级导致输出格式变化，下游解析/自动化步骤全部失效，被迫重写多个工作流。

**核心教训：**把 AI 当成外部依赖接口来管理：需要版本意识、适配层、契约测试（contract test）。

## 案例 D：跨语言"翻译代码"看似完成，实际大量 API 幻觉 {#case:code_translation_hallucination**

**现象：**AI 生成的代码大量调用不存在的方法/错误用法，表面完整但无法运行，最终需要逐文件重写与修复。

**核心教训：**复杂迁移任务要以可执行测试驱动；"生成了很多文件"不等于完成。

## 案例 E：把项目完整托付 ChatGPT，20 天后拿不到任何交付 {#case:no_delivery**

**现象：**AI 口头承诺推进、上传、优化，但最终没有任何可用代码或报告产出。

**核心教训：**AI 不能替代项目管理与交付机制：必须把任务拆成可验收的最小增量，并要求每一步都有可运行产物。

## 案例 F：ChatGPT 代写 ML 模型"漂亮地犯错"，险些造成重大损失 {#case:ml_pretty_wrong**

**现象：**离线指标很高，但因数据泄漏/类别不平衡等问题，线上预测荒谬，差点造成高额合同损失。

**核心教训：**研究与 ML 开发必须把验证债当头号风险：对照、泄漏检查、稳定性、线上/线下差异分析不可省。

## 案例 G：AI 协同编程引发版本混乱与代码"消失" {#case:version_control_mess**

**现象：**协同环境下出现文件回退、代码块消失、重复写三次功能，最终依赖 Git 历史找回。

**核心教训：**引入 AI 协作更需要严格的版本控制纪律：小步提交、频繁保存、可回滚。

## 案例 H：ChatGPT 输出不可再现，科研复现性堪忧 {#case:nonreproducible_llm_output**

**现象：**同样输入在不同时间得到不同输出，导致实验难以复现。

**核心教训：**把外部封闭模型当作"会漂移的实验仪器"：需要记录模型版本/时间戳/参数，并用稳健性评估替代单次输出结论。
