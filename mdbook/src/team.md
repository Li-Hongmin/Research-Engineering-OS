# 带学生/合作者的版本：团队最小规范

## 故事引入：从\"各自为战\"到\"互相拖累\"

你的研究团队有三个人：你（博士生）、一个硕士生学弟、一个本科生实习生。你们在做同一个项目，应该是合作关系。

**但现实是这样的：**

##### 周一早上的站会

你：\"我周末跑了新模型，效果不错，准确率 95%。\"

学弟：\"太好了！能发我代码吗？我想基于这个继续改。\"

你：\"呃......代码在我电脑上，有点乱，我整理一下再发你。\"（实际上你根本不知道从哪里开始整理）

实习生：\"我上周做的数据预处理，你们用了吗？\"

你和学弟：\"呃......用的哪个版本？\"

实习生：\"就是我发在群里的那个链接......\"（三人翻聊天记录，找不到）

导师：\"你们三个到底在做什么？为什么每个人说的数字都不一样？\"

##### 周三的代码冲突

学弟：\"师兄，我把代码 push 了，你 pull 一下。\"

你 pull 代码，结果：

    CONFLICT (content): Merge conflict in src/model.py
    CONFLICT (content): Merge conflict in configs/default.yaml
    CONFLICT (content): Merge conflict in train.py

你打开代码一看，学弟几乎改了所有文件。而且很多改动你看不懂------他加了一堆新参数，但没注释。

你花了两个小时解决冲突，最后发现：你的代码被覆盖了，上周跑出的好结果复现不了了。

##### 周五的数据灾难

实习生：\"师兄，我不小心把 data/ 目录删了，你那里有备份吗？\"

你：\"什么？！那个目录有 20GB，是我花了三天处理的数据！\"

实习生：\"我以为那是临时文件......Git 没有追踪它......\"

你和学弟都没有完整备份。你们不得不重新下载原始数据，重新运行三天的预处理流程。

**一周过去了，项目不仅没有进展，反而倒退了。**

## 为什么\"各自厉害\"不等于\"团队高效\"

团队协作的反直觉之处在于：**单个人的能力很强，但团队产出却很低**。

### 三大协作陷阱

##### 陷阱 1：隐性知识依赖

每个人脑子里都有很多\"只有自己知道\"的信息：

- 这个参数为什么设成这个值

- 这段代码为什么这么写

- 这个实验为什么失败了

- 这份数据为什么要这样处理

当需要协作时，这些隐性知识成为瓶颈------别人只能\"等你有空解释\"，而你被反复打断。

##### 陷阱 2：重复劳动

没有明确的分工和接口，导致：

- 两个人写了功能相同但实现不同的代码

- 两个人用不同方式处理同样的数据

- 两个人跑了相同的实验但记录方式不同

表面上是\"并行工作\"，实际上是\"浪费算力和时间\"。

##### 陷阱 3：集成成本爆炸

每个人在自己的分支上\"做得很好\"，但合并时发现：

- 接口不兼容

- 依赖版本冲突

- 配置方式不统一

- 评估标准不一致

最后花在\"合并和对齐\"上的时间，比各自开发的时间还多。

### 根本原因：缺少\"团队规范\"

个人项目可以\"随心所欲\"------反正只有你自己懂。

但团队项目需要**显式规范**：

- 代码怎么写

- 实验怎么记录

- 改动怎么合并

- 问题怎么沟通

**没有规范 = 每个人都在用自己的方式 = 无法协作。**

## 最小规范 1：代码规范（从混乱到可读）

### 命名规范：让代码自解释

##### 文件命名

    # ❌ 糟糕的命名
    test.py
    new.py
    model2.py
    train_final.py

    # ✅ 清晰的命名
    train_baseline.py              # 训练基准模型
    train_with_attention.py        # 训练带注意力的模型
    evaluate_on_testset.py         # 在测试集上评估
    preprocess_raw_data.py         # 预处理原始数据

##### 变量和函数命名

    # ❌ 糟糕的命名
    def f(x, y):
        z = x + y
        return z

    # ✅ 清晰的命名
    def compute_weighted_loss(prediction, target, weight):
        """
        计算加权损失

        Args:
            prediction: 模型预测 (batch_size, num_classes)
            target: 真实标签 (batch_size,)
            weight: 类别权重 (num_classes,)

        Returns:
            loss: 加权交叉熵损失
        """
        raw_loss = cross_entropy(prediction, target)
        weighted_loss = raw_loss * weight[target]
        return weighted_loss.mean()

**命名原则：**

- 用完整单词，不要缩写（除非是公认缩写如 num, max, avg）

- 函数名用动词开头（compute, load, save, train, evaluate）

- 变量名用名词（model, dataset, config, metrics）

- 布尔变量用 is/has/should 开头（is_training, has_attention, should_save）

### 注释规范：写给未来的你和队友

##### 必须注释的地方

1.  **函数文档字符串**（每个函数都要有）

          def train_one_epoch(model, dataloader, optimizer, device):
              """
              训练一个 epoch

              Args:
                  model: PyTorch 模型
                  dataloader: 训练数据加载器
                  optimizer: 优化器
                  device: 设备 ('cuda' 或 'cpu')

              Returns:
                  avg_loss: 平均损失
                  accuracy: 训练准确率
              """
              ...

2.  **不明显的逻辑**

          # 对注意力权重进行温度缩放，防止 softmax 饱和
          attention_scores = attention_scores / temperature

          # 使用 gradient clipping 防止梯度爆炸
          # 阈值设为 1.0 是基于初步实验确定的
          torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)

3.  **已知问题和 TODO**

          # TODO: 这里的实现效率不高，需要优化
          # 目前 O(n^2) 复杂度，数据量大时会很慢

          # FIXME: 当 batch size = 1 时会崩溃
          # 临时解决方案：在外层检查并跳过

          # NOTE: 这个超参数对结果影响很大
          # 改动前务必先在小数据集上测试

##### 不要注释的地方

    # ❌ 不要注释显而易见的事
    x = x + 1  # 给 x 加 1

    # ❌ 不要用注释"解释烂代码"，应该重构
    # 这个函数很复杂，做了很多事情，慢慢看...
    def complicated_function():
        ...

    # ✅ 重构成清晰的函数
    def load_data():
        ...

    def preprocess_data(data):
        ...

    def train_model(data):
        ...

### PR 模板：即使一个人也要用

Pull Request（或 Merge Request）模板强制你在合并前回答关键问题。

##### 创建 PR 模板

    # .github/pull_request_template.md

    ## 改动概述
    [用一句话描述这个 PR 做了什么]

    ## 改动类型
- [ ] 新功能 (feature)
- [ ] Bug 修复 (fix)
- [ ] 重构 (refactor)
- [ ] 文档 (docs)
- [ ] 测试 (test)

    ## 改动详情
    [详细说明改了什么、为什么改]

    ## 如何验证
    ```bash
    # 提供验证步骤
    make test
    python train.py --config configs/test.yaml
    ```

    ## 潜在风险
    [这个改动可能带来什么问题？]

    ## 相关实验
- Run ID: [如果相关，提供 run_id]
- 结果对比: [新/旧实现的指标对比]

    ## Checklist
- [ ] 代码通过 lint 检查
- [ ] 添加了必要的测试
- [ ] 更新了相关文档
- [ ] 所有测试通过
- [ ] 改动不破坏现有功能（回归测试）

**为什么\"一个人也要用\"？**

- 强制你思考\"这个改动到底做了什么\"

- 为未来的队友（或未来的你）留下清晰记录

- 养成习惯后，团队协作时自然就规范了

## 最小规范 2：实验规范（从口头到可查）

### 统一 run_id 命名

**问题：**每个人用不同方式命名实验，导致混乱。

**解决方案：**团队统一 run_id 格式。

    # 团队统一格式
    YYYY-MM-DD_HHMM_<person>_<experiment>

    例如：
    2026-02-15_1030_zhangsan_baseline
    2026-02-15_1400_lisi_attention_ablation
    2026-02-16_0900_wangwu_data_augmentation

好处：

- 按时间排序

- 知道是谁的实验（出问题时知道找谁）

- 知道实验内容

### 统一 config 管理

**问题：**每个人的 config 格式不同，无法对比。

**解决方案：**团队共享一个 base config，个人只写差异。

    configs/
      base.yaml              # 团队基准配置
      people/
        zhangsan_*.yaml      # 张三的个人实验配置
        lisi_*.yaml          # 李四的个人实验配置
      paper/                 # 论文相关的"官方"配置
        baseline.yaml
        main_method.yaml
        ablation_*.yaml

##### base.yaml 示例

    # configs/base.yaml
    # 团队基准配置，不要随意修改
    # 如有必要修改，必须在团队会议讨论

    model:
      type: "transformer"
      hidden_dim: 512
      num_layers: 6

    data:
      path: "/data/shared/project_data_v3"
      batch_size: 32
      num_workers: 4

    training:
      epochs: 100
      learning_rate: 3e-4
      optimizer: "adam"

    evaluation:
      metric: "accuracy"
      eval_every: 1000

##### 个人配置示例

    # configs/people/zhangsan_attention_test.yaml

    # 继承基准配置
    base: ../base.yaml

    # 只写差异
    model:
      attention_type: "multi_head"  # 改动点
      num_heads: 8                  # 新增参数

    # 标记实验信息
    experiment:
      owner: "张三"
      hypothesis: "多头注意力能提升 2-3% 准确率"
      related_runs:
        - "2026-02-15_1030_zhangsan_baseline"

### 统一 logging 格式

**问题：**每个人记录方式不同，无法汇总对比。

**解决方案：**使用统一的 run.json 和 run.md 模板（见第6章）。

**团队约定：**

1. 每次实验结束后 10 分钟内必须：
       - 生成 run.json（自动）
       - 填写 run.md（手动 5 行）

2. run.md 必须填写的字段：
       - 假设：这次实验想验证什么
       - 变化：相比什么改了什么
       - 结论：结果如何（一句话）
       - 下一步：基于结果下一步做什么
       - @ 导师：是否需要导师关注

3. 如果忘记记录：
       - 当周组会时会被提醒
       - 连续两次忘记：需要补齐所有缺失记录

## 最小规范 3：沟通规范（从口头到留痕）

### 周会规范：只看可复现的 run

**问题：**每周组会变成\"口头汇报比赛\"，说的天花乱坠但没有实际证据。

**解决方案：**只讨论有 run_id 的实验。

##### 周会模板

    # 每周组会（30-45 分钟）

    ## 1. 轮流汇报（每人 5-10 分钟）

    格式：
- 本周完成的实验：[列出 run_id]
- 主要发现：[基于实验数据，不是猜测]
- 遇到的问题：[具体问题，不是"不太好"]
- 下周计划：[具体目标，不是"继续调参"]

    ❌ 不接受的汇报：
- "我觉得这个方法应该有效"（没有实验支撑）
- "我跑了很多实验"（不列出 run_id）
- "效果还行"（不给出具体指标）

    ✅ 好的汇报示例：
    "我跑了三个实验：
     - 2026-02-15_1030_zhangsan_baseline: 92.0%
     - 2026-02-15_1400_zhangsan_attention: 93.5% (+1.5%)
     - 2026-02-16_0900_zhangsan_attention_v2: 93.2% (+1.2%)
    结论：注意力机制有效，但版本 v2 引入的改进反而降低了性能。
    下周计划：调查为什么 v2 更差，尝试修复。"

    ## 2. 团队决策（10 分钟）

- 哪些实验需要合并到主线？
- 哪些路径应该放弃？
- 下周谁负责什么？

    ## 3. 债务检查（5 分钟）

- 检查上周的 TODO 是否完成
- 检查是否有无记录的实验
- 检查是否有冲突的代码需要合并

    ## 4. 下周分工（5 分钟）

    明确每个人的任务和交付物：
- 张三：完成消融实验（预计 3 个 run）
- 李四：改进数据增强（预计 2 个 run）
- 王五：整理论文图表脚本

### 异步沟通规范：用文档而非口头

**问题：**队友总在不合适的时间打断你问问题。

**解决方案：**建立\"先看文档，再问人\"的文化。

##### 团队文档结构

    docs/
      README.md              # 项目总览
      SETUP.md               # 环境配置指南
      WORKFLOW.md            # 工作流程
      FAQ.md                 # 常见问题
      EXPERIMENTS.md         # 实验追踪
      DECISIONS.md           # 重要决策记录
      CONTACTS.md            # 谁负责什么

##### FAQ.md 示例

    # 常见问题

    ## Q: 如何配置环境？
    见 SETUP.md

    ## Q: 数据放在哪里？
    `/data/shared/project_data_v3`
    不要修改这个目录，只读。

    ## Q: 如何提交代码？
1. 创建分支：git checkout -b exp/your-name-feature
2. 完成改动并测试
3. 提交 PR（使用模板）
4. 等待 review
5. 合并后删除分支

    ## Q: 实验跑崩了怎么办？
1. 检查 outputs/<run_id>/error.log
2. 搜索 FAQ 看是否有类似问题
3. 如果找不到答案，在 issue 里提问（不要直接微信）

    ## Q: 如何复现别人的实验？
    make reproduce RUN=<run_id>

    ## Q: 我可以改 base.yaml 吗？
    不行。必须在团队会议讨论后才能改。
    临时测试可以创建自己的 config。

    ## Q: 我的实验结果和别人不一样，怎么办？
1. 检查是否使用了相同的 config
2. 检查是否使用了相同的数据版本
3. 检查是否使用了相同的随机种子
4. 在周会上讨论

### Issue 追踪：问题和任务可查询

**问题：**大家在微信群里讨论问题，三天后就找不到了。

**解决方案：**重要问题必须开 issue（GitHub/GitLab/Jira）。

## 导师视角：如何带学生建立好习惯

### 第一天：设定期望

**不要假设学生\"自然会做对\"。**必须明确告诉他们你的期望。

##### 入职清单

    # 新成员入职清单

    ## 第一天（环境配置）
- [ ] 配置开发环境（见 SETUP.md）
- [ ] 获得代码仓库权限
- [ ] 获得服务器访问权限
- [ ] 获得共享数据访问权限
- [ ] 阅读 README、WORKFLOW、FAQ

    ## 第一周（熟悉流程）
- [ ] 复现一个已有实验（验证环境配置正确）
- [ ] 跑一个小实验（验证理解流程）
- [ ] 完整记录实验（run.json + run.md）
- [ ] 提交第一个 PR（哪怕很小）

    ## 第一个月（独立工作）
- [ ] 独立完成一个探索方向
- [ ] 主动识别和解决问题
- [ ] 能够帮助新成员入职

### 定期 Review：不仅看结果，更看过程

**不要只在周会上问\"结果如何\"，要检查\"过程是否规范\"。**

##### 每周 Code Review 清单

    检查项：
- [ ] 本周的实验都有完整记录吗？
- [ ] Run ID 命名规范吗？
- [ ] Config 文件有更新吗？
- [ ] 代码提交 message 清晰吗？
- [ ] 有没有需要合并的改进？
- [ ] 有没有技术债需要处理？

如果发现问题，立刻指出并要求改正。**不要\"下不为例\"，否则坏习惯会固化。**

### 奖励好习惯

**明确表扬**做得好的地方：

- \"你这周的实验记录非常清晰，一眼就能看懂。\"

- \"你的 PR 描述很详细，review 很顺畅。\"

- \"你主动补充了文档，帮了大家的忙。\"

**让好习惯成为团队文化。**

## 学生视角：如何在混乱的项目中生存

### 如果项目已经很混乱

**你可能遇到：**

- 导师的代码没有文档

- 师兄的代码跑不通

- 数据不知道放在哪里

- 没有人知道某个实验是怎么跑的

**求生策略：**

##### 策略 1：为自己建立\"清洁区\"

    # 在混乱项目里创建自己的子项目

    my_workspace/
      src/           # 你的代码（不依赖混乱部分）
      configs/       # 你的配置
      outputs/       # 你的实验记录
      docs/          # 你的文档
      README.md      # 你的工作说明

即使整个项目很乱，至少你的部分是清晰的。

##### 策略 2：写下你的理解

    # docs/MY_UNDERSTANDING.md

    ## 项目目标
    [我理解的项目目标是什么]

    ## 现有代码
    [我发现的关键文件和它们的作用]

    ## 已知问题
    [我遇到的问题和临时解决方案]

    ## 我的工作
    [我负责的部分和进展]

这份文档：

- 帮你理清思路

- 未来交接时有据可查

- 可以和导师同步理解

##### 策略 3：主动建立规范

即使团队没有规范，你可以**为自己建立规范**：

- 你的所有实验都有 run_id 和记录

- 你的代码都有清晰注释

- 你的 commit 都有描述

好习惯会被注意到，可能会影响团队。

### 如何请求帮助

**❌ 糟糕的求助方式：**

\"师兄，我的代码跑不了，能帮我看看吗？\"（没有任何上下文）

**✅ 好的求助方式：**

    师兄，我在复现 baseline 实验时遇到问题，能帮忙看看吗？

    **问题**：训练到第 10 个 epoch 时崩溃，报错 CUDA out of memory

    **我的配置**：
- 分支：main
- Commit: a1b2c3d
- Config: configs/baseline.yaml
- GPU: V100 16GB

    **我尝试过的**：
1. 减小 batch size 到 16（仍然崩溃）
2. 减小模型 hidden_dim 到 256（可以跑，但结果不对）

    **日志**：见附件 error.log

    **问题**：是否有其他配置需要调整？还是需要更大的 GPU？

清晰的求助信息会得到更快、更有用的回复。

## 冲突解决：常见团队问题

### 问题 1：代码风格不统一

**解决方案：**使用自动化工具强制统一。

    # 安装 formatter 和 linter
    pip install black flake8 isort

    # .pre-commit-config.yaml
    repos:
      - repo: https://github.com/psf/black
        rev: 23.1.0
        hooks:
          - id: black

      - repo: https://github.com/PyCQA/flake8
        rev: 6.0.0
        hooks:
          - id: flake8

    # 安装 pre-commit hook
    pre-commit install

    # 现在每次 commit 前会自动格式化

### 问题 2：实验结果对不上

**排查清单：**

1. [ ] 使用的代码版本相同？（commit hash）
2. [ ] 使用的配置相同？（config diff）
3. [ ] 使用的数据相同？（数据 hash）
4. [ ] 使用的随机种子相同？（seed）
5. [ ] 使用的环境相同？（Python/CUDA 版本）
6. [ ] 评估脚本相同？（eval script）

逐项检查，总能找到原因。

### 问题 3：分工不明确导致重复劳动

**解决方案：**用看板（Kanban）可视化任务。

    # 可以用 GitHub Projects 或 Trello

    看板列：
- 待做 (TODO)
- 进行中 (In Progress)
- 等待 Review (Review)
- 完成 (Done)

    每个任务卡片：
- 标题：[简短描述]
- 负责人：[@某人]
- 截止时间：[日期]
- 依赖：[依赖其他任务]
- 状态：[当前进展]

所有人都能看到\"谁在做什么\"，避免重复。

### 问题 4：导师和学生期望不一致

**解决方案：**明确写下期望，定期对齐。

    # docs/EXPECTATIONS.md

    ## 导师期望
- 每周至少 3 个有记录的实验
- 所有代码通过 lint 和测试
- 周会准时参加并汇报
- 遇到问题 24 小时内反馈

    ## 学生期望
- 每周一次 1-on-1 答疑时间
- 关键决策会提前讨论
- 代码 review 48 小时内完成
- 论文截稿前一个月稳定需求

    ## 双方承诺
- 诚实沟通，不隐瞒问题
- 尊重彼此时间
- 共同为项目成功负责

把期望显式化，可以避免很多隐性冲突。

## 10 分钟动作：建立团队第一个规范

如果你现在只做一件事：为团队建立第一个最小规范。

1.  **如果你是导师/项目负责人**（10 分钟）

          # 创建团队规范文档
          mkdir docs
          cat > docs/TEAM_RULES.md <<EOF
          # 团队最小规范

          ## 实验记录规范
          - 每个实验必须有 run_id: YYYY-MM-DD_HHMM_name_experiment
          - 每个实验必须有 run.json（自动）和 run.md（手动 5 行）

          ## 代码提交规范
          - Commit message 格式：<type>: <description>
            - type: feat | fix | refactor | docs | test
          - 提交前运行 make test

          ## 周会规范
          - 每周一 10:00 固定时间
          - 必须提前准备：列出 run_id 和主要发现
          - 只讨论有实验证据的内容

          ## 沟通规范
          - 重要问题开 GitHub issue（不要只在微信讨论）
          - 紧急问题可以微信，但事后补 issue

          ## 生效时间
          从下周一开始执行。
          EOF

          # 在下次组会宣布并讨论

2.  **如果你是学生/团队成员**（10 分钟）

          # 为自己建立工作规范

          cat > MY_WORKFLOW.md <<EOF
          # 我的工作流程

          ## 每次实验后（5 分钟）
          - [ ] 生成 run.json
          - [ ] 填写 run.md 五要素
          - [ ] Commit 相关代码改动

          ## 每周五（15 分钟）
          - [ ] 整理本周实验列表
          - [ ] 准备周会汇报材料
          - [ ] 检查是否有遗漏的记录

          ## 每次提交代码前（2 分钟）
          - [ ] 运行 make test
          - [ ] 写清晰的 commit message
          - [ ] 如果改动重要，开 PR

          ## 每次遇到问题时
          - [ ] 先查 FAQ 和文档
          - [ ] 如果找不到答案，开 issue（描述清晰）
          - [ ] 问题解决后，更新 FAQ
          EOF

          # 从今天开始执行

3.  **下次团队会议提议**（准备 5 分钟发言）

          建议在会议上说：

          "我发现我们团队在实验记录和代码管理上有些混乱，
          建议我们建立一些最小规范，比如：
          - 统一 run_id 格式
          - 统一 config 管理方式
          - 每周检查实验记录完整性

          我草拟了一个初稿（见 docs/TEAM_RULES.md），
          大家可以讨论和补充。

          建议从下周开始试行，一个月后评估效果。"

完成这个 10 分钟动作后，你会发现：

- 团队有了一个\"起点\"------从混乱到有序的起点

- 大家有了共同语言------知道什么是\"做得好\"

- 后续可以迭代改进------而不是一直混乱下去

## 本章总结：规范不是束缚，是高效协作的基础

团队协作的悖论：

- **没有规范**：每个人都\"自由\"，但团队效率极低

- **过度规范**：流程繁琐，束缚创造力

- **最小规范**：刚好够用，既保证质量又保持灵活

**最小规范的三个层次：**

1.  **代码规范**：让代码可读、可维护、可协作

2.  **实验规范**：让实验可追溯、可对比、可复现

3.  **沟通规范**：让问题可查询、决策可追溯、分工可明确

**记住：**

- 规范不是\"管理\"工具，而是\"协作\"工具

- 规范不是\"限制\"，而是\"减少摩擦\"

- 规范不是\"一次性建立\"，而是\"持续改进\"

**最后：**如果你的团队现在很混乱，不要灰心。从一个最小规范开始，逐步改善。哪怕只有你一个人先做起来，好习惯也会慢慢影响团队。

**高效团队不是\"天生的\"，而是\"建立规范并持续执行出来的\"。**
