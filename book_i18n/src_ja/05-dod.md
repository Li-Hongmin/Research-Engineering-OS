# 「動く」から「信頼できる」への差は、一つのDefinition of Doneにある

![插图](images/05_checklist_complete.png)

## ストーリー：「だいたい終わった」の代償

![05 03 almost done trap](images/comics/05_03_almost_done_trap.png)

![完成清单](images/comics/05_checklist_hero.png)

深夜2時、ようやく「良さそう」な結果が出ました。テスト精度は94.3%、ベースラインより3ポイント向上しています。興奮してスクリーンショットを撮り、チームのグループチャットに投稿しました：「新手法の効果あり！」

3日後、論文を書き始めるにあたって、結果を再検証するために再実行しようとしました。しかし、コードを開いて躊躇しました：

- どの設定ファイルを使ったのか？似たようなYAMLが3つあり、思い出せません。
- データはどのバージョンを使ったのか？途中で一度、分割方法を一時的に変えた気がします。
- 乱数シードは何だったのか？記録を忘れました。
- 当時のコードはコミットしたのか？それとも一時的な変更を加えていたのか？

不安を感じながら再実行すると、結果は92.7%。以前より1.6ポイント下がっていました。

目の前が真っ暗になりました。どちらが正しいのか？それとも両方とも信頼できないのか？

**この状況の問題点は、「一つの実験がいつ終わったか」を判断する明確な基準がなかったことにあります。**

ソフトウェアエンジニアリングには、**Definition of Done (DoD)**（完成の定義）という概念があります。これは、「いつそのタスクが本当に完了したと言えるのか？」という問いに答えるものです。

研究においてもDoDが必要ですが、その基準は異なります：

- エンジニアリングのDoD：コードが動き、テストを通過し、ドキュメントが揃っていること。
- 研究のDoD：結果が信頼でき、再現可能で、比較可能であること。

## なぜ「動く」＝「完了」ではないのか

研究の過程には、「完成したように見えて、実は地雷が埋まっている」ケースがあまりにも多いのです。

### 地雷1：「結果は出た」が再現できない

![05 04 mine reproduce](images/comics/05_04_mine_reproduce.png)

**症状**：良い結果は見たが、完全な環境記録、設定情報、データバージョンが欠けている。数日後に再試行しても結果が一致しない。

**真のコスト**：
- 査読者に再現を求められた際に手も足も出ない。
- チームメンバーがあなたの結果に基づいて作業を継続できない。
- 最悪の場合：論文が「再現性なし」として却下される。

### 地雷2：「改善はした」が理由が分からない

![05 05 mine unknown why](images/comics/05_05_mine_unknown_why.png)

**症状**：3つの場所を同時に変更し、結果は確かに良くなったが、どの変更が効いたのか分からず、アブレーション（消融）実験も行っていない。

**真のコスト**：
- 査読者にメカニズムの説明を求められた際に答えられない。
- 今後の改善で、どれを維持し、どれを捨てるべきか分からない。
- 無効、あるいは有害な変更を重要な貢献だと誤解してしまう可能性がある。

### 地雷3：「対照実験」だが評価基準がバラバラ

![05 06 mine unfair eval](images/comics/05_06_mine_unfair_eval.png)

**症状**：自分の手法とベースラインで異なる評価スクリプトを使っているか、後処理方法が異なる。自分の手法の方が良く見えるが、実際には不公平な比較である。

**真のコスト**：
- 査読者に評価の不公平を指摘され、やり直しを求められる。
- 再実行したところ、優位性が消えてしまう。
- 評価の「公平化」のために膨大な時間を浪費する。

## 論文候補となる結論のDoDチェックリスト

以下のリストは、論文に記載される可能性のあるすべての実験結果に適用されます。チームの共通認識として、プロジェクトのREADMEにそのまま貼り付けることをお勧めします。

### 最小DoD（満たすべき5項目）

![05 07 minimal dod](images/comics/05_07_minimal_dod.png)

1.  **コマンド一つで主要指標を再現できる**

          # 例：
          make reproduce RUN=2026-02-01_1030_main_experiment
          # または：
          python reproduce.py --run_id=2026-02-01_1030_main_experiment

    ゼロの状態（与えられた環境とデータ）から、コマンド一つで論文に報告された指標を再現できる必要があります（わずかな変動は許容）。

2.  **run 记录が完全である**

    各重要な実験には、少なくとも以下を含む完全な run 記録が必要です：
    - Git commit hash（コードバージョン）
    - Config ファイルのパスと内容（すべてのハイパーパラメータ）
    - Random seed（乱数シード）
    - データバージョン（バージョン番号、ハッシュ、またはマニフェストファイル）
    - 環境の概要（Pythonバージョン、主要ライブラリ、GPUモデルなど）

    推奨されるフォーマットについては、第6章の `run.json` テンプレートを参照してください。

3.  **ベースラインとアブレーションで同一の評価スクリプトを使用している**

    すべての対照実験は以下の条件を満たす必要があります：
    - まったく同じ評価コードを使用する。
    - まったく同じデータ分割を使用する。
    - まったく同じ後処理方法を使用する。
    - 指標計算のロジックが一貫している（例：同様のしきい値、同様の平均化方法）。

    **合格基準**：統一された評価スクリプトを一つ指定でき、すべての手法の指標がそのスクリプトから得られていること。

4.  **少なくとも一つのスモークテストが1〜3分で完了する**

    スモークテスト（Smoke test）は、プロセス全体が動作することを素早く検証するテストであり、明白なエラーを早期に発見することを目的としています。

    カバーすべき重要なプロセス：
    - データ読み込み（正しく読み込まれ、正しい形状のデータが返されるか）
    - モデルのフォワードパス（クラッシュせず、出力形状が正しいか）
    - 損失計算（数値が正常か、NaNが出ていないか）
    - 評価プロセス（指標が正しく計算されるか）

    **実装案**：ごく小さなデータサブセット（例：10サンプル）を使用し、2〜3イテレーション回してプロセス全体が完結することを確認します。

5.  **図表はスクリプトで生成され、手動の編集を介さない**

    論文内のすべての図表は、`outputs/` 内の生データから自動生成される必要があります。

    禁止行為：
    - ログから数字を手動でエクセルにコピー＆ペーストする。
    - 図表のスタイルを手動で調整した後にスクリーンショットを撮る。
    - 図表の元データファイルが見当たらない。

    推奨される方法：
    - `reports/` ディレクトリに生成スクリプト（例：`plot_main_results.py`）を置く。
    - スクリプトが `outputs/<run_id>/metrics.json` を読み込み、図表を生成する。
    - 図表を編集可能な形式（PDFなど）と元データ（CSVなど）で保存する。
    - Makefile に `make plots` を追加し、ワンクリックですべての図表を生成できるようにする。

### 強化DoD（推奨される追加項目）

![05 08 enhanced dod](images/comics/05_08_enhanced_dod.png)

最小DoDを満たした上で、以下の項目を満たすことで、結果の信頼性をさらに高めることができます：

1.  **複数回実行による統計的な結果**
    ランダム性の大きい実験では、一回の実行だけでは有効性を証明できません。推奨：
    - 少なくとも3〜5個の異なる乱数シードで実行する。
    - 平均値と標準偏差（または信頼区間）を報告する。
    - run 記録に、すべてのシードに対応する run_id を列挙する。

2.  **失敗ケースの分析**
    手法の限界を正直に記録します：
    - どのような場合に効果が薄いのか？
    - 明らかな失敗サンプルはあるか？
    - ハイパーパラメータへの感度はどの程度か？
    これは信頼性を高めるだけでなく、今後の改善の方向性も示してくれます。

3.  **完全なアブレーション実験**
    複数の改善を含む手法については、アブレーション実験（消融実験）を行い、以下の問いに答える必要があります：
    - 各改善は単独でどれだけ貢献しているか？
    - どの改善が重要で、どれが周辺的なものか？
    - 改善間に相互作用はあるか？

4.  **コード品質チェック**
    自動化ツールを使用してコード品質をチェックします：
    - Linter（flake8, pylintなど）：コードスタイルのチェック
    - Type checker（mypyなど）：型チェック
    - 単体テストのカバレッジ：重要な関数には必ずテストがあること
    これらをCIで自動的に実行します。

5.  **データリークのチェック**
    トレーニングセットとテストセットが厳密に隔離されていることを確認します：
    - データ分割前にサンプル数を出力し、総数が一致するか確認する。
    - トレーニングセットとテストセットに重複がないか確認する（サンプルIDやハッシュを使用）。
    - 時系列データの場合：テストセットの時間がトレーニングセットより後であることを確認する。

## DoDチェックリスト： 「動く」から「信頼できる」への操作手順

![质量门](images/comics/05_quality_gate.png)

### 実験終了直後に行うこと（5分）

1.  **run 情報を記録する**
          # run.json を自動生成する（第6章のツールを利用）
          python log_run.py --run_id <id>
2.  **run.md に重要な情報をメモする**（5行以内）
    - この実験の仮説は何か？
    - 主な変更点は何か？
    - 結果はどうだったか（一文で要約）？
    - 次に何を計画しているか？
    - 注意すべきリスクや異常はあるか？

### 論文を書く前に行うこと（30分）

1.  **再現性の検証**
    新しいターミナル（または新しい環境）で再現コマンドを実行します：
          make reproduce RUN=<論文候補のrun_id>
    チェック項目：
    - エラーなく動作するか？
    - 結果が妥当な範囲内か（差が1〜2%以内、または標準偏差の範囲内か）？
    - 差が大きい場合、原因を特定する（環境、データ、ランダム性）。
2.  **対照実験のチェック**
    比較対象となるすべての手法を確認します：
          ls outputs/
          # すべてのベースラインとアブレーションの run_id を見つける
    確認事項：
    - すべて同じ評価スクリプトを使用しているか？（run.json のパスやハッシュで確認）
    - データ分割は一致しているか？
    - 評価パラメータは一致しているか？
    不一致が見つかった場合は、該当する実験を再実行し、評価基準を統一する必要があります。
3.  **スモークテストの実行**
          make test
          # または：
          pytest tests/test_smoke.py
    その後の変更によってコアプロセスが壊されていないことを確認します。
4.  **図表の生成**
          make plots
    生成された図表を確認します：
    - 最新の実験結果が反映されているか？
    - 数値が run 記録と一致しているか？
    - 軸、凡例などが明確か？

### 論文投稿前に行うこと（1時間）

1.  **網羅性のセルフチェック**
    DoDチェックリストに照らし合わせ、一項目ずつ確認します：
    - 論文で引用しているすべての実験に run_id があること。
    - すべての run_id に完全な run.json があること。
    - すべての対照実験で同一の評価スクリプトを使用していること。
    - スモークテストを通過していること。
    - すべての図表がスクリプトで生成可能であること。
2.  **重要な実験にGitタグを打つ**
          # 主要な実験
          git tag -a result-main-table2 -m \
            "Main results in Table 2, run_id: 2026-02-01_1030_main"

          # アブレーション実験
          git tag -a result-ablation-table3 -m \
            "Ablation study in Table 3, run_ids: 2026-02-01_14*"

          # タグをプッシュ
          git push origin --tags
3.  **再現ドキュメントの作成**
    READMEまたは独立した REPRODUCE.md に以下の情報を記述します：
    - 環境構築手順（コマンド一つ、またはスクリプト）。
    - データ準備手順（ダウンロード、前処理）。
    - 各表/図を再現するためのコマンド。
    - 予想される実行時間とリソース要件。
    例：
          # 再現手順

          ## 環境構築
          conda env create -f environment.yaml
          conda activate research-env

          ## データ準備
          bash scripts/download_data.sh
          python scripts/preprocess.py

          ## 主要実験の再現（Table 2）
          make reproduce RUN=2026-02-01_1030_main
          # 予想時間：2時間（V100シングル基）
          # 予想指標：accuracy 94.3% ± 0.5%

          ## アブレーション実験の再現（Table 3）
          bash scripts/reproduce_ablation.sh
          # 予想時間：6時間（V100シングル基）

## チームでのDoD活用法

![05 09 team dod](images/comics/05_09_team_dod.png)

### マージ基準として
チーム開発において、DoDをメインブランチへのマージ基準にできます：
1.  実験ブランチを main にマージするには、最小DoDを満たす必要があります。
2.  コードレビュー時には、レビューアーがDoDチェックリストに従って確認します。
3.  DoDを満たさないコードはマージできず、不足分を補う必要があります。

### 引き継ぎ基準として
プロジェクトの引き継ぎ（卒業、離職など）の際、DoDは知識の流出を防ぎます：
- すべての重要な実験に完全な記録があり、新しいメンバーが再現できる状態であること。
- コード品質が保証されていること（テスト、ドキュメント）。
- データとモデルの保存場所およびアクセス方法が明確であること。

### セルフチェック基準として
個人プロジェクトであっても、DoDは「自分を騙す」ことを防いでくれます：
- 定期的（例：毎週）に、DoD未完了の実験をチェックし、記録を補完する。
- 論文執筆前にまとめてチェックし、土壇場でのパニックを避ける。
- 習慣にすることで、DoDが自然なワークフローの一部となり、追加の負担ではなくなります。

## よくある障害と解決策

### 障害1：「今はただ探索しているだけだから、厳しくする必要はない」
**反論**：探索段階では**DoD基準を緩和しても良い**ですが、基準をゼロにしてはいけません。
推奨される「探索段階の簡易DoD」：
- 複数回の統計結果は求めない。
- 完全なアブレーション実験は求めない。
- **ただし、以下は必須**：コミット、config、シードを記録し、再実行可能であることを保証すること。
実験に「価値がありそうだ」と分かった時点で、即座にフルDoDへアップグレードします。

### 障害2：「DoDを満たすには時間がかかりすぎる」
**回答**：一度30分投資することで、以下のメリットが得られます：
- 査読時に慌てて補完する必要がなくなる（数日の節約）。
- 今後の改善に明確なベースラインができる（重複作業の節約）。
- 論文投稿時に「再現できない」という不安がなくなる（精神的負担の軽減）。

**実践的なアドバイス**：
- DoDチェックをスクリプト化し、手作業を減らす。
- Gitの pre-commit hook にチェックを組み込む（第7章）。
- 慣れてしまえば、DoDは日常業務に溶け込み、余計なコストではなくなります。

### 障害3：「すでに実験管理ツール（MLflowやW&Bなど）を使っている」
**回答**：ツールは非常に有用ですが、DoDはツールではなく**基準**です。
ツールは以下の手助けをしてくれます：
- run 情報の自動記録（時間の節約）。
- 実験結果の可視化（比較の容易化）。
- モデルや産物の保存（管理の利便性）。

しかし、ツールは以下の代わりにはなりません：
- 「何をもって完了とするか」というあなたの定義。
- 「評価が公平か」というあなたのチェック。
- 「コードが再現可能か」というあなたの検証。

**提案**：DoDチェックリストとツールを組み合わせましょう。例えば、MLflowの run に「DoDを満たしているか」というフィールドを記録するなどです。

## 10分アクション：現在最も有望な結果にDoDチェックを適用する

もし今すぐ一つだけ行うなら：現在あなたが持っている「最も有望な」実験結果に、一度完全なDoDチェックを行ってみてください。

1.  **その実験の run_id を特定する**（なければ今すぐ作成する）
2.  **run 記録を確認する**
          # run.json があるか確認
          ls outputs/<run_id>/run.json

          # なければ即座に補完：
          # 1. gitコミットを記録：git log -1 --format="%H"
          # 2. config ファイルのパスを記録
          # 3. シードを記録（覚えていれば）
          # 4. データバージョンを記録（データディレクトリやログを確認）
          # 5. 環境を記録：pip freeze > requirements_<run_id>.txt
3.  **再現を試みる**
          # 記録されたコミットに切り替え
          git checkout <commit_hash>

          # 記録された config で再実行
          python train.py --config <config_path> --seed <seed>

          # 結果が妥当な範囲内にあるか確認
4.  **チェック結果を記録する**
    `outputs/<run_id>/dod_check.md` に以下を記録します：
    - 記録は完全か？
    - 再現可能か？（結果の差異：）
    - 評価は公平か？
    - テストはあるか？
    - 図表は生成可能か？
5.  **問題が見つかれば即座に修正する**
    - 記録不足：run.json を補充する
    - 再現不可：原因を調査し、再実行する
    - 評価不公平：評価スクリプトを統一し、すべての対照実験を再実行する

このチェックを終えることで、あなたはその結果の信頼性について明確な認識を持つことができます。DoDを通過していれば、自信を持って論文に書くことができます。通過していなければ、今この瞬間に修正するのが最善の策です。

**忘れないでください：問題は、論文投稿前よりも今見つける方が良く、査読時よりも論文投稿前の方が良く、論文発表後に疑問を投げかけられるよりも査読時の方が良いのです。**
