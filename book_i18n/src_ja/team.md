# 学生・共同研究者向け：チームの最小限の規範

![イラスト](images/10_team_collaboration.png)


## イントロダクション：「個別の戦い」から「互いの足を引っ張り合う関係」へ

![チームミーティング](images/comics/10_team_standup.png)

あなたの研究チームには3人のメンバーがいます。あなた（博士課程）、修士課程の後輩、そして学部生のインターンです。同じプロジェクトに取り組んでおり、本来は協力関係にあるはずです。

**しかし、現実はこうです。**

### 月曜朝のスタンドアップミーティング

![10 05 monday standup](images/comics/10_05_monday_standup.png)

あなた：「週末に新しいモデルを回してみたよ。結果は良好で、精度は 95% だった。」
後輩：「すごいですね！ そのコードを共有してもらえませんか？ 私もそれをベースに変更を加えたいです。」
あなた：「あー……コードは自分のPCにあるんだけど、まだ散らかっていて。整理してから送るよ。」（実際には、どこから整理すればいいのか見当もつきません）
インターン：「僕が先週やったデータの前処理、皆さんは使いましたか？」
あなた・後輩：「えーっと……どのバージョンのこと？」
インターン：「ほら、チャットにリンクを貼ったやつです……」（3人でチャットをさかのぼりますが見つかりません）
指導教官：「君たちは一体何をやっているんだ？ なぜ全員が言っている数字がバラバラなんだ？」

### 水曜日のコードの衝突（コンフリクト）

![10 06 wednesday conflict](images/comics/10_06_wednesday_conflict.png)

後輩：「先輩、コードをプッシュしたので、プルしてください。」
あなたがプルした結果：
```text
CONFLICT (content): Merge conflict in src/model.py
CONFLICT (content): Merge conflict in configs/default.yaml
CONFLICT (content): Merge conflict in train.py
```
コードを開いてみると、後輩はほとんどすべてのファイルを書き換えていました。しかも、追加された大量の新しいパラメータにはコメントがなく、意図が分かりません。
コンフリクトの解消に2時間を費やした挙句、あなたのコードが上書きされていたことに気づき、先週の良好な結果が再現できなくなってしまいました。

### 金曜日のデータの災難

![10 07 friday data disaster](images/comics/10_07_friday_data_disaster.png)

インターン：「先輩、間違えて `data/` ディレクトリを消してしまいました。バックアップはありますか？」
あなた：「何だって？！ あのディレクトリには 20GB もあって、僕が3日間かけて処理したデータが入っていたんだぞ！」
インターン：「てっきり一時ファイルかと思って……。Git も追跡していなかったし……」
あなたも後輩も完全なバックアップを持っておらず、結局、元データをダウンロードし直して3日間の前処理をやり直すことになりました。

**一週間が過ぎましたが、プロジェクトは進展するどころか、後退してしまいました。**

## なぜ「個々の能力」が「チームの効率」に直結しないのか

チーム開発の直感に反する事実は、**「一人一人の能力が高くても、チーム全体の成果が低いことがある」** という点です。

### 3つのコラボレーションの落とし穴

#### 落とし穴1：暗黙知への依存
![10 08 hidden knowledge](images/comics/10_08_hidden_knowledge.png)
人々の頭の中には「その人しか知らない」情報が詰まっています。
- なぜこのパラメータをこの値にしたのか
- なぜこのコードはこのように書かれているのか
- なぜこの実験は失敗したのか
- なぜこのデータをこのように処理したのか
協力が必要になったとき、これらの暗黙知がボトルネックになります。他人は「あなたが説明してくれるのを待つ」しかなく、あなたは何度も作業を中断されることになります。

#### 落とし穴2：重複作業
![10 09 duplicate work](images/comics/10_09_duplicate_work.png)
明確な分担やインターフェースがないと、以下のようなことが起こります。
- 目的は同じだが実装が異なるコードを複数人が書く。
- 同じデータに対して異なる方法で前処理を行う。
- 同じ実験を異なる形式で記録する。
表面上は「並行作業」ですが、実際には計算資源と時間の無駄遣いです。

#### 落とし穴3：統合コストの爆発
![10 10 integration explosion](images/comics/10_10_integration_explosion.png)
各自が自分のブランチで「素晴らしい仕事」をしていても、マージの段階で問題が露呈します。
- インターフェースの不整合。
- 依存ライブラリのバージョン衝突。
- 設定（config）の方法がバラバラ。
- 評価基準が不統一。
結局、「統合と調整」にかかる時間が、各自の開発時間を上回ってしまいます。

### 根本原因：「チームの規範」の欠如
個人のプロジェクトなら、自分さえ分かれば「気の赴くまま」にやっても問題ありません。
しかし、チームのプロジェクトには **明文化された規範（ルール）** が必要です。
- コードをどう書くか
- 実験をどう記録するか
- 変更をどうマージするか
- 問題をどう共有するか
**規範がない ＝ 全員が自分勝手なやり方をしている ＝ 協力は不可能。**

## 最小限の規範1：コード規範（混乱から可読性へ）

![コードレビュー](images/comics/10_code_review.png)

### 命名規則：コードに語らせる

![10 11 naming convention](images/comics/10_11_naming_convention.png)

#### ファイル命名
❌ **悪い例**：
`test.py`, `new.py`, `model2.py`, `train_final.py`

✅ **良い例**：
`train_baseline.py` (基底モデルの訓練), `train_with_attention.py` (Attention付きの訓練), `evaluate_on_testset.py` (テストセットでの評価), `preprocess_raw_data.py` (元データの前処理)

#### 変数と関数の命名
❌ **悪い例**：
```python
def f(x, y):
    z = x + y
    return z
```

✅ **良い例**：
```python
def compute_weighted_loss(prediction, target, weight):
    """
    重み付き損失を計算する

    Args:
        prediction: モデルの予測値 (batch_size, num_classes)
        target: 正解ラベル (batch_size,)
        weight: クラスごとの重み (num_classes,)

    Returns:
        loss: 重み付きクロスエントロピー損失
    """
    raw_loss = cross_entropy(prediction, target)
    weighted_loss = raw_loss * weight[target]
    return weighted_loss.mean()
```

**命名の原則**：
- 略語を使わず、完全な単語を使う（一般的な略称 `num`, `max`, `avg` 等は除く）。
- 関数名は動詞で始める（`compute`, `load`, `save`, `train`, `evaluate`）。
- 変数名は名詞にする（`model`, `dataset`, `config`, `metrics`）。
- 真偽値（Boolean）は `is`, `has`, `should` で始める（`is_training`, `has_attention`, `should_save`）。

### コメントの規範：未来の自分と仲間のために

#### コメントが必須の場所
1. **関数の docstring**（すべての関数に含める）。
2. **直感的でないロジック**（なぜその処理が必要なのか）。
   ```python
   # Softmaxの飽和を防ぐため、アテンションスコアを温度でスケーリングする
   attention_scores = attention_scores / temperature
   ```
3. **既知の問題と TODO**。
   ```python
   # TODO: ここの実装は効率が悪いので、最適化が必要
   # FIXME: batch size = 1 の時にクラッシュする問題の暫定対応
   # NOTE: このハイパーパラメータは結果に大きく影響するため注意
   ```

#### コメントすべきでない場所
❌ 当たり前のことは書かない（`x = x + 1 # xに1を足す`）。
❌ 「汚いコード」をコメントで説明せず、リファクタリングする。

### PR テンプレート：一人の時でも使う

![10 12 pr template](images/comics/10_12_pr_template.png)

Pull Request（または Merge Request）のテンプレートは、マージ前に重要な質問に答えることを強制します。

#### PR テンプレートの例 (`.github/pull_request_template.md`)
- 改動の概要（何を、なぜ変えたか）
- 変更の種類（新機能、バグ修正、リファクタリング、ドキュメントなど）
- 検証方法（テストの実行コマンドなど）
- 潜在的なリスク
- 関連する実験 (`run_id`)

**なぜ一人でも使うのか？**
- 「この変更で結局何をしたのか」を自分に再確認させるため。
- 未来の仲間（あるいは未来の自分）のために明確な記録を残すため。
- 習慣化することで、チーム開発時に自然に振る舞えるようになるため。

## 最小限の規範2：実験規範（口頭から追跡可能へ）

### run_id 命名の統一
全員が異なる方法で実験に名前をつけると、すぐにカオスになります。
**解決策**：チームで `run_id` のフォーマットを統一します。
`YYYY-MM-DD_HHMM_<担当者名>_<実験内容>`
例：`2026-02-15_1030_suzuki_baseline`

### 設定（config）管理の統一
一人の変更で基底設定が壊れないよう、チーム共有の `base.yaml` を用意し、個人は「その差分」だけを記述するようにします。
```text
configs/
  base.yaml              # チーム共通のベースライン設定
  people/
    suzuki_*.yaml        # 個人用の実験設定
  paper/                 # 論文用の「公式」設定
```

### ログ（logging）形式の統一
全員が同じ形式で `run.json` と `run.md`（第6章参照）を生成することを約束します。
- 実験後、自動的に `run.json` が生成されること。
- 手動で5行、`run.md`（仮説、変更点、結論、次のステップ）を記入すること。

## 最小限の規範3：コミュニケーション規範（口頭から記録へ）

### 週次ミーティングの規範：再現可能な run だけを見る
週次の定例会が「口頭だけの実績報告会」にならないようにします。
- `run_id` がない実験については議論しない。
- 「〜な気がする」という推測ではなく、「実験データに基づいた発見」を報告する。
- 良い報告の例：「3つの実験 `run_id...` を行い、Attentionが1.5%向上することを確認しました。しかし、V2での改良は逆に性能を下げました。来週はその原因を調査します。」

### 非同期コミュニケーションの規範：記録を優先する
「まずはドキュメントを確認し、それでも分からなければ質問する」文化を築きます。
- **チームドキュメントの構成**： `README.md` (概要), `SETUP.md` (環境構築), `WORKFLOW.md` (フロー), `FAQ.md` (よくある質問).
- チャットで流れてしまう重要な議論は、必ずドキュメントや **Issue（課題）** に残します。

## 指導教官の視点：学生に良い習慣を身につけさせる方法

### 初日に期待値を設定する
学生が「自然に正しくやってくれる」と期待してはいけません。期待値を明確に伝えます。
- **オンボーディング・リスト**：
  - [ ] 環境構築の完了（`SETUP.md` を参照）。
  - [ ] 既存の実験の一つを再現してみる（環境が正しいか確認）。
  - [ ] 実験の完全な記録（`run.json` + `run.md`）を行う。
  - [ ] 最初の PR を出す（どんなに小さくても可）。

### 定期的なレビュー：結果だけでなくプロセスも
週次ミーティングで「結果はどうだったか」と聞くだけでなく、「プロセスが規範に従っているか」をチェックしてください。
- 今週の実験にはすべて記録があるか？
- `run_id` の命名は正しいか？
- PR の説明は十分か？
問題があればその場で指摘し、修正を求めます。「今回だけは大目に見よう」は、悪い習慣を定着させる原因になります。

## 学生の視点：混乱したプロジェクトの中で生き残る方法

### もしプロジェクトがすでに混乱しているなら
- 師匠のコードにドキュメントがない、動かない。
- データがどこにあるか分からない。
そんな状況での生存戦略は以下の通りです。

1. **自分専用の「クリーンゾーン」を作る**：
   プロジェクト全体がカオスでも、自分の作業ディレクトリ内だけは、本ガイドで勧める手法を使って徹底的に整理し、記録を残します。
2. **自分の理解を書き残す**：
   自分が理解したプロジェクトの目標、発見した主要ファイル、直面した問題と暫定対策を、自分用の README にまとめます。これは自分の思考整理になると同時に、将来の引き継ぎ資料にもなります。
3. **自ら規範を提案する**：
   「実験の結果を整理しやすくするために、名前の付け方を統一しませんか？」と、メリットを提示しながら提案してみましょう。

## コンフリクトの解決：よくあるチームの問題

- **コードスタイルがバラバラ**： `Black` や `Flake8` などの自動化ツール（Linter/Formatter）を導入し、 `pre-commit hook` で強制的に統一します。
- **実験結果が合わない**：コミット、設定、データ、シード、環境、評価スクリプトの6項目を一つずつ対照させれば、必ず原因が見つかります。
- **役割分担が不明確**： `GitHub Projects` や `Trello` などの看板（Kanban）を使い、タスクを可視化します。

## 10分間アクション：チームの最初の規範を作る

今すぐできることが一つあるとすれば、チームのために最初の「最小限の規範」を明文化することです。

1. **プロジェクトリーダーの場合**：
   `docs/TEAM_RULES.md` を作成し、`run_id` の付け方、コミットメッセージの形式、週次ミーティングのルールを5分で書き上げてください。そして次回の会議で共有しましょう。
2. **メンバーの場合**：
   自分のための作業規範を `MY_WORKFLOW.md` に書き出しましょう。実験後の記録、金曜日の整理、PR前のテストなど、自分自身のルーチンを固定します。
3. **次回の会議で提案する**：
   「最近、実験の管理が大変になってきたので、管理を楽にするために最小限のルールを決めませんか？」と提案してみてください。

## 本章のまとめ：規範は束縛ではなく、効率的な協力の基盤である

![チームの勝利](images/comics/10_team_victory.png)

チーム開発のパラドックスはこうです。
- **規範がない**：全員が「自由」だが、チームとしての効率は極めて低い。
- **規範が過剰**：手続きが煩雑になり、創造性が損なわれる。
- **最小限の規範**：品質を保ちつつ柔軟性も維持できる、ちょうど良いバランス。

**最小限の規範の3つの階層**：
1. **コード規範**：読みやすく、保守しやすく、協力しやすいコードにする。
2. **実験規範**：追跡可能で、比較可能で、再現可能な実験にする。
3. **コミュニケーション規範**：課題が検索可能で、意思決定が追跡可能で、役割が明確なコミュニケーションにする。

**最後に**：もしあなたのチームが現時点で混乱していても、がっかりしないでください。まずは一つの小さな規範から始め、段階的に改善していけばよいのです。たとえあなた一人から始めたとしても、その良い習慣は必ずチーム全体に波及していくはずです。

**「効率的なチーム」は生まれつき存在するのではなく、規範を作り、それを継続的に改善していく過程で生まれるものなのです。**
