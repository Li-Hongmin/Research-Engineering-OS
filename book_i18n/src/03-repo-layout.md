# 你的仓库结构就是你的第二大脑

研究代码的"混乱"通常不是因为能力不足，而是因为研究本质上是平行探索：同时需要维护多个假设、多种实现、多个实验入口、多种输出和多张图表。

当这些东西没有结构地堆在一起时，你的大脑被迫充当索引：**哪个脚本还能跑？哪个输出值得信任？哪个改动影响了指标？**

仓库结构的目的不是为了好看，而是为了**降低认知负荷**：让你能够判断——不依赖记忆——"这个代码能删吗？这个输出可靠吗？这条路径可重复吗？"

## 真实案例：快速堆积代码的代价

![从混乱到整洁](images/comics/03_messy_to_clean.png)

当我刚开始用AI编码助手时，就学到了这个惨痛的教训。为了快速验证一个想法，我让Copilot生成了大量"能跑"的代码——数据加载、模型定义、训练循环、评估脚本等等。几小时内，我就建立了看起来完整的框架。

### 早期的"成功"：

![03 04 early success](images/comics/03_04_early_success.png)

代码确实能跑，实验产生了结果。兴奋之余，我继续迭代，不断要求AI添加新功能：数据增强、不同的模型变体、各种评估指标...每个改动都有"立竿见影"的效果，代码库迅速膨胀。

#### 崩溃的开始：

![03 05 collapse begins](images/comics/03_05_collapse_begins.png)

两周后，当我需要为论文准备消融实验和对比实验时，问题浮出水面：

- 不知道哪个脚本是最新的，哪个已经过时；

- 同样的数据加载逻辑被复制粘贴到五个不同的文件里，每个都有细微差异；

- baseline和新方法用了不同的评估代码，结果根本无法比较；

- 想复现"很好的结果"，却找不到当时用的配置和数据版本。

#### 重新开始：

![03 06 rewrite pain](images/comics/03_06_rewrite_pain.png)

最后，我不得不停止所有新实验，花了三整天**重写几乎所有代码**。这个重写不是因为AI生成的代码有bug，而是因为**缺乏结构**：可复用的核心逻辑和一次性的实验脚本混在一起；临时凑合的试验代码没有及时清理；输出散落各地难以追踪。

这个经历让我深刻理解：AI能帮你快速生成代码，但**结构必须由人来设计**。如果从一开始就分离"稳定"和"探索"，按run_id整理输出，后来就不会陷入这种混乱。

#### 案例启示：

这不是孤例。当你用AI快速堆积"能跑"的仓库，却没有把可复用代码和一次性实验入口隔离开时，常见的结局就是：每个模块都要重写，AI生成的碎片几乎全部被替换。**结构是防止这种返工的第一道防线。**

## 抄作业式的目录布局（对研究友好）

![完美的目录结构](images/comics/03_folder_tree.png)

```
repo/
  src/                 # 核心库：可复用、可测试、可维护（慢变量）
  experiments/         # 实验入口：一次性胶水代码（快变量，可丢弃）
  configs/             # 统一配置：yaml/json格式（可diff、可追踪）
  data/                # 仅放指针或小样本；大数据在外部管理
  outputs/             # 运行产物：按run_id整理（可清理/可归档）
  reports/             # 论文图表和结论：从outputs里自动生成
  scripts/             # 工具脚本：数据准备/下载/评估等
  tests/               # 单元测试 + 冒烟测试（守住底线）
  Makefile             # 常用入口：train/eval/reproduce/test
  README.md
  CLAUDE.md            # AI编码规则（推荐）
```

## 快变量 vs. 慢变量：分离"稳定"和"探索"

![快慢变量分离](images/comics/03_fast_slow_variables.png)

建议把仓库的内容分成两类：

- **慢变量（稳定）**：会长期维护、反复复用、需要测试覆盖的部分。

- **快变量（探索）**：快速验证假设的入口脚本、短生命周期的胶水代码、一次性分析。

在本书的术语里：`src/` 包含慢变量，`experiments/` 包含快变量。

**经验法则**：探索可以脏，但核心库必须干净；探索可以快，但评估必须稳定。

### 为什么这个分离这么重要？

在我的重写经历中，最大的痛点是**无法区分资产和消耗品**。当所有代码混在一起时，你不敢删（怕删掉重要功能），也不敢大改（怕影响其他实验）。一旦明确定义 `src/` 为资产、`experiments/` 为消耗品，心理负担就大大降低了：

- 修改 `src/` 要慎重，需要测试；

- 修改 `experiments/` 可以随意——试验完就删。

## 各目录的完成定义（DoD）

一个目录名字只有在"什么应该放进去"和"什么不应该放进去"足够清晰时，才能真正减少混乱。

### src/：核心库（可复用、可测试）

![03 07 src directory](images/comics/03_07_src_directory.png)

- 放可复用的模块：数据加载、模型组件、损失函数、评估、通用工具。

- 必须可测试：至少要有冒烟测试覆盖关键流程。

- 不要硬编码：不要放只对某次运行有用的路径/参数。

#### 反面例子：

在我的重写案例中，原来的"数据加载"代码硬编码了某个具体实验的路径和预处理方式，逼得新实验只能复制粘贴再修改。如果从一开始就把路径和参数作为函数参数传入，就不会出现这个问题。

### experiments/：实验入口（可丢弃）

![03 08 experiments directory](images/comics/03_08_experiments_directory.png)

- 只放入口和胶水：**允许短生命周期**；用完就删。

- 任何被证明有价值且可复用的逻辑，稳定后都应该迁移到 `src/` 里。

#### 实用建议：

用日期或run_id给每个实验脚本命名，比如 `2026-02-01_baseline.py`。这样一眼就能看出哪些实验老了，哪些是新的。定期（比如每周）清理一个月以上没价值的旧脚本。

### configs/：配置（可追踪）

- 每个"论文候选结论"都必须对应一个config（或一个可追踪的生成方式）。

- config必须能展开到最终参数（避免默认值漂移）。

### outputs/：产物（可清理/可归档）

- 只放运行产物，按**run_id整理**。

- 不要覆盖：不要重用或手工修改同一个run_id目录。

- 归档重要产物：把它们转移到长期存储；仓库里不要背着大二进制文件。

### reports/：图表和结论（可再生成）

- 尽量只放脚本生成的图表/表格和草稿结论。

- 论文里的所有图表都必须能从 `outputs/` 里复现，避免手工拖拽。

### tests/：测试（守住底线）

- 至少一个1-3分钟的冒烟测试：跑通数据加载→前向传播→损失→评估。

- 给关键函数加断言：形状、NaN、数值范围、数据泄露信号等。

## 汇聚入口：让"怎么跑"显而易见

![03 09 makefile entry](images/comics/03_09_makefile_entry.png)

研究中最常见的浪费是：别人（包括未来的你）不知道怎么跑代码。

建议把常用的入口汇聚到一个 `Makefile`（或等价的任务工具）里：

- `make test`

- `make train CONFIG=...`

- `make eval RUN=...`

- `make reproduce RUN=...`

当入口足够少、足够稳定时，你能在内部保持复杂性，对外暴露可复现性。

## 渐进式重构：从混乱项目迁移到规范结构

如果你已经有一个"混乱"的遗留项目，不要试图一次性推倒重来。下面是循序渐进的重构过程：

### 第1步：识别和分离快变量 vs. 慢变量

1. **审视现有代码**：扫描整个项目，标记哪些模块是核心功能（长期维护、反复复用），哪些是一次性实验脚本。

2. **新建目录**：

- 新建 `src/`，把你确定会复用的模块迁移进去；

- 新建 `experiments/`，把各种运行脚本和临时代码都挪进去。

3. **完成粗粒度分层**：完成这一步后，项目结构就会清晰多了，脑子里的索引负担也会减轻。不追求完美，只要把明显的部分分开就行。

### 第2步：提取配置和参数

1. **找出硬编码值**：扫描代码，找所有硬编码的关键参数（学习率、batch大小、路径等）。

2. **创建配置文件**：在 `configs/` 下创建YAML或JSON文件，集中管理参数。

3. **增量替换**：不要一次性改所有代码。改一个脚本，确认能跑后再改下一个。

#### 实战经验：

单单是提取配置，我在重构中就发现了三个隐藏的bug——不同脚本里"看似相同"的参数其实取值不同，导致结果无法比较。

### 第3步：标准化输出路径

1. **定下规约**：决定用 `outputs/<run_id>/` 这样的结构。

2. **修改代码**：调整所有实验入口，让输出都按run_id归档。

3. **清理旧输出**：整理或删除散落的历史输出文件，保持outputs目录干净。

### 第4步：添加基础测试

1. **写冒烟测试**：创建一个1-3分钟的快速测试，验证核心流程端到端能跑。

2. **每次重构后跑**：确保改动没有破坏基础功能。

3. **逐步增加覆盖**：随着重构进行，逐步为关键函数加单元测试。

#### 核心原则：

渐进性很重要。不要试图一次性完成所有重构；每一步都要确保现有功能完好后再进行下一步。我的重写花了三天，但如果从一开始就采用渐进式重构，完全可以分散在一周内，不影响实验节奏。

## 多任务/多项目的目录层级管理

面对多个相关但独立的研究任务时，目录怎样组织就成了关键问题。

### 原则：优先用独立仓库

**最佳实践**：每个研究项目用一个独立的代码仓库。好处是：

- 避免跨项目的依赖冲突；

- 版本控制相互独立；

- 简化复现（每个项目自己的环境和依赖）。

#### 经验法则：

如果两个项目在依赖版本、数据集或运行环境上有明显差异，**强烈建议分开成独立仓库**。

### 单仓库里的多项目分层结构

如果你确实要在一个仓库里管理多个相关任务（比如同一篇论文的多个实验，或共享很多代码的子项目），可以用这样的结构：

```
repo/
  projectA/
    src/
    experiments/
    configs/
    outputs/
    README.md
  projectB/
    src/
    experiments/
    configs/
    outputs/
    README.md
  common/
    src/               # 项目间共享的核心代码
    tests/             # 共享代码的测试
    scripts/           # 通用工具脚本
  README.md            # 整体说明
  Makefile             # 跨项目常用命令
```

### 命名规约和环境隔离

- **配置文件命名**：用项目前缀，比如 `configs/projectA_baseline.yaml`、`configs/projectB_ablation.yaml`。

- **输出目录**：可以在各项目子目录下维护outputs，也可以在仓库根合并，用项目名前缀：`outputs/projectA/<run_id>/`。

- **环境管理**：即使代码在一个仓库里，也建议给不同项目维护独立的虚拟环境或Docker容器，避免依赖冲突。

### 何时共享代码 vs. 何时复制代码

**何时共享到 common/**：

- 多个项目都需要的基础工具函数；

- 通用的数据加载或预处理逻辑；

- 标准的评估指标计算。

**何时直接复制**：

- 代码还在快速变化，不同项目的需求可能分化；

- 共享会造成过度耦合，伤害独立性；

- 项目临近完成，未来不太可能一起同步更新。

#### 实战建议：

早期优先复制；只有在代码真正稳定、你确信需要共享时，才提取到 common/。过度抽象导致共享代码频繁修改，反而增加维护负担。

## 快速开始：用AI生成你的仓库模板

为了加快这个过程，导师建议你用AI助手。简单描述一下需要的目录结构和文件——比如，给Claude发一句话：

> "为我生成一个标准的研究项目模板，包含这些目录：src/、experiments/、configs/、outputs/、data/、reports/、scripts/、tests/。给每个目录加上说明注释，再生成一个README.md解释各目录用途，以及一个Makefile，包含test、train、eval、reproduce这些目标。"

一分钟内，完整的项目结构和所有基础文件就生成了。你现在有了一个坚实的基础，还没写一行代码——这就是"站在巨人的肩膀上"的意思。从此以后，你决定每个新项目都用这种方式开始。

### 为什么这很重要

用AI生成样板代码不是懒惰，而是**结构智慧**。把繁琐的模板创建外包给AI，你保证了每个项目一开始就遵循最佳实践。人的精力就能专注到独特的科学问题上，不是重复造轮子。

## 10分钟行动：给你的项目"分层一次"

如果你现在就能做一件事，那就是把当前仓库粗略分成快变量和慢变量。

1. 新建 `src/`，把你确定会复用的模块放进去。

2. 新建 `experiments/`，把所有入口脚本放进去，允许它们短生命周期。

3. 新建 `configs/`，从脚本里提取关键参数。

4. 把所有输出标准化到 `outputs/<run_id>/`。

你会立刻感受到"可控感"的提升，因为你开始区分什么是资产、什么是消耗品。

### 来自个人经验：

如果我一开始用AI编码助手时就建立了这个结构，那三天的重写完全可以避免。好的结构不是为了美观，而是为了**停止让大脑充当索引**，让仓库本身成为你可靠的"第二大脑"。
